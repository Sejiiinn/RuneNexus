# 리더보드 1차 설계

작성: 2026-09-08. 상태: 구현 및 로컬 검증 완료. 로비 커밋 `ee95082` 이후 작업이다. 운영 반영 시 migration 009와 서버·클라이언트 배포가 필요하다. 기존 저장 JSON 형식은 유지한다.

## 목적과 범위

로비의 리더보드에서 다른 플레이어의 최고 진행도와 내 순위를 확인한다. 첫 버전은 계정별 최고 기록을 비교하는 상시 진행도 랭킹으로 권장한다. 시즌, 랭킹 보상, 타임어택, 친구 순위, 전투력 점수는 후속 범위다. 현재 서버는 전투를 재현하지 않으므로 경쟁 보상을 붙이기 전 별도 기록 검증 설계가 필요하다.

## 순위 규칙

| 항목 | 제안 |
|---|---|
| 대상 | 활성 계정, 닉네임 설정 완료, 유효한 서버 정산 기록 보유 |
| 1순위 | 최고 기록의 스테이지 번호 내림차순 |
| 2순위 | 해당 스테이지의 완료 라운드 내림차순 |
| 3순위 | 같은 스테이지·완료 라운드이면 최고 기록의 서버 확정 시각 오름차순 |
| 완전히 같은 기록·시각 | 공동 순위 허용; 목록 내 순서는 내부 계정 ID로 고정 |
| 화면 표시 | 순위 / 닉네임#태그 / 스테이지 / 완료 라운드 |
| 갱신 | 정산된 새 기록이 기존 기록보다 좋을 때만 교체 |
| 시작만 한 전투 | 완료 라운드 0은 순위 등록 제외 |
| 판정 시점 | 성공·실패 등 기존 전투 종료 정산이 서버에서 완료된 시점 |

예: 스테이지 4의 1라운드 완료는 스테이지 3의 40라운드 완료보다 높다. 진입 중인 라운드 번호와 완료 라운드를 혼동하지 않는다. 동일 기록이면 서버 확정 시각이 빠른 사람이 높은 순위다. 예를 들어 같은 스테이지 14·38라운드를 10:00에 확정한 계정은 10:05에 확정한 계정보다 높다. 시각까지 정확히 같은 경우에만 공동 순위를 적용하고 내부 계정 ID는 목록 순서만 고정한다. `success`도 별도 가산점으로 사용하지 않는다.

현 정산 범위는 스테이지 1~15, 완료 라운드 0~40이다. 마지막 스테이지까지 같은 기록을 달성해도 먼저 서버에서 확정한 기록이 위에 온다. 클리어에 걸린 시간이 짧은 순서가 아니라, 해당 기록을 먼저 확정한 순서다. 플레이 시간·재화는 정렬에 사용하지 않는다.

## 화면과 상태

로비의 기존 버튼에서 안전영역 높이 84%의 리더보드 모달을 연다. 가장자리에 어둡게 처리한 로비가 보인다. 제목·닫기·내 순위는 고정하고 순위 목록만 스크롤한다. 닫으면 원래 로비로 돌아간다. 신규 최상위 탭을 추가하지 않는다.

상단에는 `리더보드`, `전체 순위 · TOP 100`, 닫기, 새로고침을 배치한다. 본문은 상위 100명 목록, 하단은 목록과 별도로 유지되는 `내 순위` 행이다. 내 계정이 목록에도 있으면 강조한다. 동일 기록도 확정 시각이 다르면 서로 다른 순위를 표시한다. 도움말은 `동일 기록은 먼저 달성한 순 · 서버 확정 시각 기준`이며 행을 누르면 서버 확정 시각을 표시한다. 닉네임과 태그, 스테이지·라운드 문구를 생략하지 않고 줄바꿈으로 수용한다.

- 로딩: 로딩 표시. 성공 전 가짜 순위나 예시 사용자를 노출하지 않는다.
- 빈 목록: `아직 등록된 기록이 없습니다.`
- 내 기록 없음: `전투 기록을 동기화하면 순위에 등록됩니다.`
- 정산 대기: 로컬 기록으로 순위를 추측하지 않고 마지막 서버 기록과 동기화 대기 상태를 표시한다.
- 게스트/닉네임 미설정: 기존 계정 화면으로 안내한다. 1차 조회 API는 기존 계정 인증을 요구하는 안으로 범위를 제한한다.
- 통신 실패: 기존 성공 결과가 있으면 갱신 실패 안내와 함께 유지하고, 없으면 오류·재시도 화면을 표시한다.
- 계정 전환/로그아웃: 이전 계정 결과와 진행 중 요청 결과를 폐기한다.

매 프레임 또는 상시 폴링하지 않는다. 화면 진입과 수동 새로고침 시 조회하며, 앱 재개·정산 완료 후 열린 화면 갱신은 기존 상태 알림과 연결한다. 작은 화면과 글자 2배에서도 목록·닫기·내 순위 접근을 검증한다.

## 기존 구조와 연결

`lib/game/rune_nexus_game.dart`의 `_settleRunResult`는 성공 시 전체 라운드, 실패 시 완료 라운드를 계산한다. `lib/game/systems/run_progression.dart`의 `finishRun`과 `bestRoundsByStage`가 로컬 최고 기록을 관리한다.

`server/internal/economy/run_rewards.go`의 `SettleRun`은 요청 범위, writer, 저장 revision, 저장 progression과 정산 결과를 대조하고, 요청 키와 계정별 run 보상 키로 중복 지급을 방지한다. `economy_reward_claims`에는 runId, 스테이지, 완료 라운드, 성공 여부와 서버 접수 시각이 남는다.

새로운 점수 제출 API를 만들지 않는다. 기존 `POST /v1/economy/runs/settle`의 성공 트랜잭션에 최고 기록 갱신을 추가한다. 보상 정산과 랭킹 기록은 함께 커밋 또는 롤백된다. DB 장애는 기존 정산 재시도로 복구하고, 랭킹 조회 장애가 게임 시작을 막지 않게 한다. 기존 정산 요청·응답 계약은 유지한다.

## 데이터와 조회 API 제안

새 테이블 `leaderboard_records`를 추가한다. 기존 저장 JSON은 변경하지 않는다.

| 필드 | 의미 |
|---|---|
| board_key, rules_version, account_id | 계정별 최고 기록의 복합 키 |
| stage_number, completed_rounds | 정렬 기준 |
| source_command_id | 원본 서버 정산 연결 |
| achieved_at | 해당 최고 기록을 처음 서버 정산한 시각. 서버 DB 시계로 생성하며 동점 판정에 사용 |

`board_key=progression`, `rules_version=1`로 시작한다. 버전은 시즌이 아니라 비교 규칙·스테이지 구성 변경을 구분하기 위한 값이다. 동일/낮은 기록은 시각과 원본 연결까지 덮어쓰지 않는다. 동시 정산은 조건부 upsert로 더 좋은 기록만 보존한다. 정렬용 인덱스를 추가하고 sqlc 생성 파일은 기존 생성 경로로 갱신한다.

`GET /v1/leaderboards/progression`을 기존 인증 미들웨어 아래 추가한다. 응답은 `rulesVersion`, `asOf`, `entries`(상위 100명), `myEntry`(없으면 null)다. 각 행은 `rank`, `displayName`, `stageNumber`, `completedRounds`, `achievedAt`(UTC), `isMe`를 담는다. 내부 계정 UUID·이메일·Google 식별자는 반환하지 않는다. 표시명은 기존 닉네임·4자리 태그 규칙을 재사용한다.

순위는 활성·닉네임 설정 계정만 먼저 필터링한 전체 집합에서 `RANK() OVER (ORDER BY stage_number DESC, completed_rounds DESC, achieved_at ASC)`로 계산한 뒤 상위 목록과 내 행을 선택한다. 목록 100명 밖에서도 내 실제 순위를 반환한다. 공동 순위가 100명 경계를 걸쳐도 목록은 최대 100행만 보여준다. 첫 버전은 페이지 이동 없이 상위 100명으로 제한한다. 조회 내 목록과 내 순위는 하나의 일관된 DB 스냅샷을 사용한다.

## 기록 이관과 신뢰도

권장 정책은 기능 도입 이후 서버 정산된 기록부터 등록하는 것이다. 과거 로컬 최고기록이나 클라이언트 저장 JSON으로 순위를 소급 생성하지 않는다. 기존 최고기록이 높은 플레이어도 도입 이후 정산한 전투가 첫 랭킹 기록이 된다는 점을 등록 안내에 명시한다. 오프라인 전투는 기존 계정 정산 경로로 동기화가 성공했을 때만 반영하며 그 서버 정산 시각을 사용한다. 기기 시계는 조작될 수 있어 클라이언트가 전송한 클리어 시각을 동점 판정에 사용하지 않는다. 현재는 라운드별 서버 통지가 아닌 전투 종료 정산이므로 온라인에서도 실제 라운드 클리어 순간과 서버 확정 시각에 차이가 있다. 실시간 클리어 순간 자체를 비교하려면 라운드별 검증·서버 기록 경로가 별도로 필요하다.

도입 경계는 서버 활성화 시각으로 고정한다. 활성화 이전에 이미 발급된 정산 영수증의 재시도는 랭킹에 새로 등록하지 않는다. 도입 이후 정산의 영수증 재시도는 원래 트랜잭션에서 집계가 완료되어 있어 중복 영향을 주지 않는다. 배포 시 기존 운영 데이터에서 활성화 경계를 검증한다.

현재 저장 progression은 클라이언트 JSON을 기반으로 한다. 서버 정산과 저장 대조는 전투 결과의 진위를 보장하지 않는다. 새 runId와 조작한 저장을 이용한 허위 기록 가능성이 남는다. 이를 사용자에게 `완전 검증된 경쟁 기록`으로 표현하지 않는다. 구현 중 스테이지·라운드·성공 조합 검사를 보강할 경우 기존 정산 호환성을 먼저 확인한다.

시즌/경쟁 보상을 도입하려면 서버 발급 run 식별, 시작 시 장비·규칙 버전 고정, 기록 검증 수준, 의심 기록 제외·복구 정책을 먼저 별도 설계한다. 타임어택은 현재 정산에 신뢰 가능한 경과시간이 없으므로 그 단계에서 다룬다.

## 구현 순서와 검증

1. 위 순위·범위·기존 기록 등록 정책을 기준으로 DB migration, query, leaderboard 서비스 구현.
2. 기존 정산 트랜잭션에서 조건부 최고 기록 갱신. 영수증 재시도·동시 요청·롤백 검증.
3. 인증 조회 API와 상위 100명·내 순위 조회 구현. 비활성 계정 제외 및 표시명 노출 검증.
4. Flutter API/model과 기존 인증 갱신 경로 연결. 로비 버튼의 안내 팝업을 실제 화면으로 교체.
5. 초기 빈 상태, 게스트, 로그인 만료, 네트워크 오류, 계정 전환, 작은 화면·글자 확대, 실기 렌더 검증.

핵심 테스트: 스테이지 우선 비교, 동일 스테이지 라운드 비교, 동일 진행도에서 먼저 확정한 기록 우선, 기록·시각까지 같은 경우 공동 순위, 재도전·재시도로 최초 시각 보존, 더 높은 기록 갱신 시 새 시각 사용, 0라운드 제외, 낮은 기록으로 퇴행 방지, 동일 run 재요청, 동시 최고 기록 갱신, 정산 실패 시 집계 미반영, 100위 밖 내 순위, 과거 영수증 등록 제외. 기존 계정·저장·경제 정산 회귀 테스트를 함께 수행한다.

변경 후보: 기존 `server/internal/economy/run_rewards.go`, `server/internal/httpapi/handler.go`, `server/cmd/api/main.go`, `lib/app/rune_nexus_app.dart`, `lib/ui/menu/main_menu_lobby.dart`. 신규 leaderboard SQL migration/query, 서버 service/handler, Flutter API/model/화면. 기존 경제 서비스를 광범위하게 재구성하거나 외부 랭킹 서비스를 추가하지 않는다.

## 구현 및 배포 메모

- 새 테이블은 migration 적용 시 비어 있다. 이미 완료된 정산은 기존 영수증 경로에서 반환하므로 소급 등록하지 않는다. 서버 코드 활성화 이후 새로 완료되는 정산부터 집계한다.
- Flutter 조회는 기존 `OnlineAccountSessionController`의 인증 갱신을 재사용한다. 열린 모달은 서버 정산 성공 알림으로 다시 조회하고 계정이 바뀌면 이전 응답을 폐기한다.
- 운영 화면에는 예시 데이터가 없다. 디자인 검증 데이터는 `test/leaderboard_dialog_test.dart`에만 있으며 `design/leaderboard/implemented_preview.png`는 그 예시를 실제 위젯으로 렌더한 이미지다.
- 운영 DB 변경과 배포는 수행하지 않았다. 신규 정산 코드는 새 테이블을 사용하므로 migration `009_leaderboard_records.sql`을 서버 코드보다 먼저 적용한다. 기존 저장·경제 데이터를 재작성하지 않는다.
- 서버 테스트는 격리 PostgreSQL에서 migration 001~009, 정산 원자성·재시도·순위 비교를 검증한다. 클라이언트는 API 오류·인증 만료·응답 경합·계정 전환·반응형·로비 연결을 검증한다.
