역할: 다음 구현 세션이 실행할 설계와 실험 순서. 작성: 2026-09-13. **제작 방향은 합의됐으며, 첫 실험은 2026-09-13에 내장 후보 미채택으로 기록했다.** [첫 실험 결과·Android 비교·APK·미검증 범위](../design/stage1_3d/native_material_workflow/verification/first-native-20260913/README.md)를 따른다. 내장 재질 전환과 승인 표현의 시각 이관은 완료하지 않았다.

2026-09-13 후속: 사용자 승인에 따라 화면 굴절 없는 내장 PBR·공용 환경 반사를 적용했다. [후속 적용 결과](../design/stage1_3d/native_material_workflow/verification/native-reflection-20260913/README.md). 아래 첫 실험의 실행 순서와 당시 상태는 설계 기록이며 현행 재질 설정은 후속 기록을 따른다.

## 1. 목표와 첫 실행 범위

소재의 빛 반응은 Godot 내장 PBR 재질에 맡기고, Blender에서 만든 형태·표면 정보를 게임까지 일관되게 전달한다. 새 에셋마다 광학 계산을 작성하지 않고, 검증된 소재 설정과 조명 환경을 재사용한다. 엔진 내장 재질도 시각 검증은 필요하며 Blender Cycles와 동일한 결과를 보장하지 않는다.

다음 세션의 첫 목표는 **현재 코어에 내장 StandardMaterial3D를 적용한 비교 결과를 만들고, 대표 석재·금속과 함께 실제 Android 화면에서 채택 가능성을 판단하는 것**이다. 코어 하나가 만족스럽지 않은 상태에서 모든 에셋을 일괄 교체하지 않는다. 기존 지형·금속이 이미 내장 재질을 사용한다면 비교의 기준으로 재사용한다.

첫 실행에 포함하는 작업:

- 기존 코어와 내장 재질 코어를 동일 조건에서 비교하는 국소 구현, 필요한 공용 재질 설정, 관련 검증 갱신.
- 원본 텍스처·정점색·노멀 보존 여부 확인과 잘못된 연결의 국소 수정.
- 대표 에셋 비교 후 필요한 공용 조명·반사 설정 조정. 재질 변경과 분리하여 전장 전체 영향 확인.
- 비교 이미지, 실제 Android 캡처, 설치용 로컬 APK, 채택/미채택 이유와 다음 작업 인계.

첫 실행에서 하지 않는 작업: 전장 재배치, 코어 형태 변형, 게임 카메라 재설계, 전투·저장·브리지 계약 변경, 기존 VFX 전면 교체, Forward+ 전환, 엔진 버전 변경, 외부 플러그인·의존성 추가, 공개 배포. 기존 시안의 형태와 시점 차이를 재질 변경으로 덮지 않는다.

현재 확인한 실행 구조:

- `godot/project.godot`: Godot 4.7 계열 Mobile 설정. 빌드 도구는 공식 4.7.2와 Android AAR 버전을 맞춘다.
- `godot/main.gd::_ready`: GLB 로딩 후 정점색을 준비한다. 코어의 `core_crystal_facets` 표준 재질을 `core_crystal.gdshader`의 ShaderMaterial로 덮는다. 포탈과 추가 식생도 별도 커스텀 재질을 쓴다.
- 현재 코어는 원본 색·거칠기·금속성·발광을 uniform에 복사하고, importer가 생략한 투과율·굴절률을 GLB extras로 읽는다. 이것은 원본 수치 전달이지 Blender의 광학 계산을 이식한 것이 아니다.
- 코어 반사는 맵당 128px ReflectionProbe 한 개를 한 번 캡처한다. 정적 지형·받침을 캡처하며 결정만 반사를 수신한다. 결정 전용 보조 방향광도 한 개 있다.
- 현재 환경은 FILMIC 톤매핑, 색 기반 환경광, 주 방향광·보조 방향광이다. 기존 문서의 ThreeJS 면광원·PMREM·AgX 설명을 현재 Godot 구현으로 오인하지 않는다.
- `verify_scene.gd`에 `--crystal-glass`, `--crystal-camera-comparison` 비교 경로가 있다. 기존 검수 경로를 확장하고 별도 렌더러·웹 검수 앱을 만들지 않는다.

코어 진단에서는 동일 GLB의 Blender 방향 카메라 고도가 약 49.6도, 게임은 약 62.7도였다. 같은 배율의 결정 실루엣 세로/가로 비율은 각각 약 2.00, 1.50이었다. 원본 변형으로 보상하지 말고 아래 두 비교를 구분한다.

1. **이관 비교**: 최종 GLB·투영·카메라 방향·피벗·배율·결정 회전 위상을 맞춰 원본 표현과 비교한다.
2. **게임 수용성 비교**: 현재 게임의 고정/드론 카메라와 실제 HUD 아래 크기에서 확인한다. 진단용 카메라를 본게임 기본값으로 반영하지 않는다.

## 3. 원본과 엔진 설정의 책임

| 항목 | 기준 위치 | 운영 규칙 |
| --- | --- | --- |
| 형태·면 분할·베벨·노멀·UV·피벗·정점색 | 에셋별 `.blend`와 최종 GLB | Blender 원본에서 수정. 게임에서 늘리기·기울이기·발광선으로 형태를 재해석하지 않음 |
| Base Color·Metallic·Roughness·Normal·AO·Emission | Blender의 내보낼 PBR 데이터 | GLB 임포트 결과의 데이터와 텍스처 참조를 보존. 노드 그래프의 절차적 표면 정보는 필요할 때 해당 채널에 베이크 |
| 투명 모드·굴절 기능·컬링·텍스처 필터·렌더 우선순위 | Godot 내장 재질 설정 | 원본 의도를 실시간 엔진에서 구현하는 설정. 원본 속성과 의미가 다르면 명시적으로 구분 |
| 주광·보조광·환경 반사·노출·톤매핑·Glow | 공용 Godot 장면 | 실제 엔진 화면을 보고 조정. 에셋마다 보정용 광원을 생성하지 않음 |
| 회전·부유·피격·정지·배속 | 기존 런타임 상태와 노드 변환 | 재질 교체와 독립적으로 유지 |

Base Color/Emission 색 데이터와 Non-Color인 Normal/ORM 데이터를 혼동하지 않는다. 정점색의 선형/sRGB 처리, Base Color와의 곱셈, OpenGL 방향의 노멀과 tangent를 확인한다. 기존 색을 두 번 감마 변환하거나 정점색을 빠뜨리지 않는다.

베이크 대상은 표면의 색·요철·거칠기·정적인 차폐 정보다. 카메라에 고정된 반짝임, 광원 하이라이트, 동적 그림자를 Base Color에 그려 넣어 실시간 재질을 대신하지 않는다. 새 재질 때문에 텍스처를 무조건 증설하지 않으며 현재 atlas·UV·해상도를 먼저 재사용한다.

ORMMaterial3D는 AO/Roughness/Metallic을 RGB로 묶어 쓰는 선택지이며 화질 상위 버전이 아니다. 현재 StandardMaterial3D가 이미 채널이 패킹된 텍스처를 올바르게 읽고 있다면 이름을 바꾸기 위한 전환은 하지 않는다. Clearcoat는 코팅층 소재에만 사용하고 크리스탈을 좋게 만드는 필수 옵션으로 취급하지 않는다. Toon/Rim/윤곽선은 현재 승인 방향을 대신하지 않는다. [Godot 내장 재질 기능](https://docs.godotengine.org/en/stable/tutorials/3d/standard_material_3d.html)

## 5. 코어 실험과 채택 방법

### 5.1 비교 조건 고정

기존 `verify_scene.gd` 안에서 같은 장면·결정 인스턴스의 재질만 바꾸어 순차 캡처한다. 실험 옵션은 검수 스크립트에 두고 사용자 설정·저장 형식에는 추가하지 않는다.

- A: 현재 커스텀 코어. 변경 전 회귀 기준이다.
- B: GLB의 실제 임포트된 내장 재질. 원본 전달 상태를 확인하는 기준이며 유리의 완성 결과로 취급하지 않는다.
- C: B를 출발점으로 내장 Refraction 등 엔진 설정을 적용한 코어. 첫 채택 후보다.

각 비교는 같은 GLB 해시·메시 bounds·카메라·뷰포트·결정 회전/부유 위상·배경·조명·노출을 사용한다. 굴절은 배경에 의존하므로 코어만 투명 배경에 띄운 결과로 평가하지 않는다. 비교 도중 게임 카메라나 원본 형태를 함께 바꾸지 않는다. Blender와 Godot의 광원 단위/알고리즘은 다르므로 수치 동일성을 조명 동일성으로 주장하지 않는다. 동일 조건은 우선 Godot A/B/C 사이에서 보장하며, Blender 비교에는 조명 구성과 차이를 기록한다.

### 5.2 내장 유리 설정의 의미

현재 원본의 Roughness 0.055, Metallic 0, 청록 면색과 발광을 먼저 보존한다. 원본 Transmission 0.80·IOR 1.46은 제작 의도를 기록하는 값이다. **Godot의 `refraction_scale`에 IOR를 넣거나 알파를 `1 - Transmission`으로 자동 변환하지 않는다.** 이 속성들은 동일한 광학 의미를 갖지 않는다.

내장 Refraction는 화면 공간 효과이며 투명 경로를 사용한다. 배경 굴절을 보려면 Albedo alpha 조정이 필요할 수 있다. 이 알파는 Godot 쪽 설정으로 따로 기록하고 Blender 원본의 Alpha 1을 덮어쓰지 않는다. 현재 커스텀 셰이더의 ALPHA=1을 새 구현에 강제하지 않으며, 반대로 알파만 낮춘 흐릿한 코어를 완료 결과로 채택하지 않는다.

내장 방식은 자기 자신/다른 투명체의 다중 굴절과 화면 밖 물체를 정확히 표현하지 못한다. 앞쪽 물체가 굴절에 섞이는 현상, 투명 정렬, 받침/포탑/입자와의 겹침도 확인한다. 기존 커스텀의 깊이 검사 기능이 자동 보존된다고 가정하지 않는다. 이런 차이가 핵심 표현을 훼손하면 해당 한계를 기록하고 채택하지 않는다. 곧바로 새로운 광학 셰이더를 작성하지 않는다. [내장 굴절의 동작과 한계](https://docs.godotengine.org/en/stable/tutorials/3d/standard_material_3d.html#refraction)

### 5.3 코드에 반영할 경계

- 현재 `main.gd`의 `core_crystal_facets` 매칭 지점에서 표준 재질을 선택한다. 다른 surface·받침·포탈 재질을 전체 override하지 않는다.
- GLB mesh의 원본 surface material을 기준으로 시작한다. 이미 적용된 ShaderMaterial override를 원본처럼 복사하지 않는다.
- 후보 재질은 로딩 시 한 번 만들고 모든 코어에 공유한다. 인스턴스별·프레임별 duplicate, 텍스처 재로드, shader 계산 함수 추가는 하지 않는다.
- 기존 `_prepare_vertex_colors`, 결정 레이어, 반사 수신, 부유·회전·피격·정지 계약을 유지한다. 투명 코어의 그림자는 엔진 지원과 실제 결과를 확인해 결정한다.
- 채택 시 현재 코어 전용 ShaderMaterial 생성·uniform 전달과 불필요해진 preload를 제거한다. 원본 Transmission/IOR metadata는 데이터로 남길 수 있지만, 내장 경로가 사용하지 않는 값의 존재를 실행 필수 조건으로 요구하지 않는다.
- `verify_runtime.gd`의 ShaderMaterial 타입·공유 shader·uniform 전제는 새 계약에 맞게 교체한다. 단일 결정, 내부 자식 없음, 규격, 공유 재질, 애니메이션 검증은 유지한다.

실험이 끝나면 A/B/C 임시 전환을 본게임에 남기지 않는다. 비교 캡처와 결과 기록을 보존하고, 채택 재질 하나를 공용 런타임에서 사용한다. 미채택이면 기존 경로를 보존하고 실패 이유를 남긴다.

## 6. 재사용 프리셋과 재임포트

처음에는 소재 라이브러리 전체를 만들지 않는다. 코어에서 검증된 공통 설정부터 `godot/materials/`의 내장 `.tres`로 정리한다. 이 경로와 아래 운영 방식은 **구현 예정**이다.

- 원본 그대로 충분한 재질: GLB 임포트 재질 사용.
- 엔진 설정이 필요한 재질: 예를 들어 `core_glass.tres`에 투명·굴절·필터 등 엔진 설정을 보관한다. 런타임에서 프리셋을 한 번 복제하고, GLB의 Base Color/색 텍스처·Metallic/Roughness 및 채널·Normal/AO·Emission·UV/정점색 관련 원본 데이터를 보존해 공유한다. 실제 존재하는 데이터만 연결하고 검증한다.
- 원본 데이터와 프리셋 값을 이중으로 수동 관리하지 않는다. 엔진용 알파처럼 의도적으로 다른 값만 프리셋이 담당하며, 그 차이는 프리셋 옆 README에 적는다. 원본 색이 바뀌면 재내보내기·재임포트 후 게임에 반영되어야 한다.
- 수작업 숫자를 `main.gd` 곳곳에 분산하지 않는다. 다만 단일 프리셋 연결을 위해 범용 MaterialManager·새 import 프레임워크·단순 wrapping helper를 만들지 않는다.
- 재질 매칭은 기존 노드와 안정된 material 이름을 사용한다. 이름 변경 시 조용히 기본 재질로 넘어가지 말고 누락을 알려준다.

Godot의 외부 재질 추출도 가능하지만, 이 저장소의 `build/godot/project`는 생성물이다. 생성 디렉터리에서만 편집한 `.tres`/`.import`를 원본으로 삼지 않는다. 외부 재질은 재임포트 때 원본 값과 자동 동기화되지 않고 재질 이름 변경에도 영향을 받으므로, 첫 실험은 위의 명시적 연결을 우선한다. [외부 재질과 재임포트](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/advanced_import_settings.html#extracting-materials-to-separate-files)

프리셋 옆 기록에는 소재 목적, 원본 GLB/material 이름, 엔진 전용 설정, 공유 범위, 사용 텍스처, 확인한 카메라/Android 캡처, 남은 제한을 적는다. 검증 전 설정을 모든 에셋의 기본값으로 승격하지 않는다.

## 7. 조명과 반사 정책

먼저 현재 조명으로 재질 A/B/C를 비교한다. 그다음 필요할 때 조명을 별도 변경하여 석재·금속·코어를 함께 확인한다. 목표는 참고 이미지의 소재 구분과 차가운 환경/따뜻한 국소광 대비이며, 모든 표면을 어둡게 만들어 대비를 흉내 내지 않는다.

- 현재 Mobile 렌더러를 유지한다. ReflectionProbe, 기본 조명, 톤매핑과 필요한 Glow부터 활용한다. SDFGI·SSR 등 Forward+ 기능을 이번 성공의 전제로 삼지 않는다.
- 코어 반사 프로브의 현재 개수·해상도·한 번 캡처를 첫 예산으로 유지한다. 정적 지형/받침 캡처와 결정 수신을 그대로 비교한다.
- 금속에 반사가 부족하면 이후 동일 프로브의 수신 범위 확장 또는 공용 환경 반사를 평가한다. 반사로 밝아진 주변 소재까지 검수한다. 개체별 프로브·매 프레임 캡처를 기본 해법으로 쓰지 않는다.
- 결정 전용 보조광은 최초 A/B/C에서 고정한다. 내장 재질 채택 이후 필요성이 없어졌을 때만 제거하고 결과를 재확인한다. 에셋 수만큼 보정 광원이 늘어나는 구조로 확장하지 않는다.
- Glow는 발광의 주변 번짐이 필요한 경우에만 조정한다. 형태·면색이 날아갈 정도의 발광으로 굴절 부족을 숨기지 않는다.
- LightmapGI는 고정 환경의 후속 후보로만 둔다. 동적 설치/철거·적·포탑의 음영과 베이크된 정적 환경을 구분하며 이번 대표 재질 실험에 도입하지 않는다.

지원 기능은 [Godot 렌더러 비교](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html), Blender 광원의 수치 복사보다 엔진에서 최종 조명을 검수하는 원칙은 [모델 이관·조명 지침](https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/importing_3d_scenes/model_export_considerations.html#lighting-considerations)을 따른다.

## 8. 커스텀 효과를 유지하는 경계

내장 재질 우선은 기존 커스텀 효과 일괄 제거 지시가 아니다. 포탈 소용돌이, 풀 정점 바람, 포구 연기·포탄 체적 효과는 현재 동작과 승인된 입체 표현을 보존한다. 특히 기존 포탄 폭발을 Billboard나 평면 아틀라스로 바꾸지 않는다.

새로운 커스텀이 필요하다고 판단할 때는 내장으로 만든 비교 결과, 부족한 핵심 표현, 모바일 비용을 먼저 적는다. 기존 범위에서 해결 가능한 기능만 국소 추가한다. 표면 조명 계산은 가능한 한 엔진 기본을 유지하고 고유한 움직임·효과 데이터만 다룬다. 필요하면 내장 재질을 shader로 변환해 출발할 수 있지만, 변환한 코드는 이후 엔진 업데이트가 자동 반영되는 내장 재질과 달라 유지보수 대상이다. VisualShader도 같은 엔진 shader를 만드는 저작 도구이며 Cycles 렌더러를 도입하는 기능은 아니다. [VisualShader 설명](https://docs.godotengine.org/en/stable/tutorials/shaders/visual_shaders.html)

## 9. 다음 세션 실행 순서와 검증

| 단계 | 실행 | 통과/중단 기준 |
| --- | --- | --- |
| 1. 현재 상태 보존 | 작업 트리 확인, 변경 전 대상 파일/GLB 해시와 관련 Android 결과 보존 | 다른 진행 작업을 reset하거나 초기 생성기로 덮지 않음 |
| 2. 대표 비교 | 코어 A/B/C, 같은 지형 석판·받침 금속 또는 기존 대포를 같은 조건에서 확인 | 재질만 바뀌었음을 확인. 이관 시점/게임 시점 결과를 구분 |
| 3. 원인별 조정 | 임포트 연결 → 내장 재질 → 공용 조명 순으로 차이를 분리 | 핵심 결함이 남으면 원인과 한계를 기록. 여러 변수를 동시에 바꾸며 새 시안을 만들지 않음 |
| 4. 국소 채택 | 통과한 코어 재질과 실제 재사용할 프리셋만 공용 런타임에 연결 | 기존 형태·애니메이션·공유·정지·타일 계약 유지 |
| 5. Android 확인 | 동일 PCK를 사용하는 APK에서 아래 대표 상태 확인 | 데스크톱 캡처나 headless 성공만으로 모바일 시각 완료 처리하지 않음 |
| 6. 인계 | 채택/미채택 결과, 이미지·APK·로그·비용 비교와 미검증 항목 기록 | 성공한 검사 반복 금지. 핵심 차이가 없으면 픽셀 차이만으로 재조정하지 않음 |

시각 성공 기준:

- 코어의 실제 결정면과 청록 면색이 구분되고, 시점/회전에 따라 반사 하이라이트가 변한다. 전체가 흐릿한 투명 덩어리나 불투명 평면색으로 보이지 않는다.
- 파란 발광 윤곽선·내부 불투명 덩어리를 추가하지 않는다. 받침은 고정되고 결정만 움직인다.
- 같은 카메라에서 원본의 실루엣이 유지된다. 현재 게임 카메라에서도 코어의 식별성이 유지되며, 시점 차이를 완전한 형태 이관 실패와 혼동하지 않는다.
- 석재 요철과 거칠기 변화, 금속과 도장면의 차이를 유지한다. 공용 조명 변경으로 바닥·적·포탑 가독성을 훼손하지 않는다.
- 고정/드론 시점에서 코어와 받침·앞쪽 포탑·뒤쪽 지형이 겹칠 때 사라짐·정렬 오류·심한 굴절 번짐이 없다. 관련 투명 입자와 겹치는 상태도 한 번 확인한다.

검사와 비용:

- `scripts/build_godot_pack.py`로 소스 동기화·임포트·PCK를 준비하고, `verify_runtime.gd`의 관련 계약 검사를 실행한다. GPU 비교에는 `verify_scene.gd`를 사용한다. 시각 판단을 픽셀 변화량 임계치만으로 대체하지 않는다.
- 실제 Android 검증은 [인앱 가이드](../.agents/in_app_test_guide.md)와 [공용 빌드](stage1_3d_preview.md)를 따른다. 재질 확인용 로컬 APK를 제공하고, 본게임의 고정/드론 전환·관련 타일 선택과 HUD 겹침을 확인한다. 로그인·저장 전체 검사는 그 경계를 바꾼 경우에만 확대한다.
- 원본이 여러 타일에서 재사용되는 계약은 대표 다른 지면/다중 코어 배치로 확인한다. 공유 재질 수가 인스턴스 수만큼 늘어나지 않는지 검사한다.
- 전후 같은 기기·빌드 모드·전투 조건에서 draw call, material/texture 수, 메모리와 프레임 시간을 비교한다. 굴절의 화면 읽기·투명 중첩 비용은 별도 관찰한다. 내장 재질이라는 이유만으로 빨라졌다고 보고하지 않는다.
- 실기기 접근 시 기존 기준인 4배속 다중 착탄과 지속 전투의 p95/p99·발열 후 저하를 확인한다. 목표 60fps/약 16.7ms와 현재 미확정인 지원 하한 기종을 구분한다. 실기기가 없으면 가능한 Android 시각 검증을 끝내고 실기기 성능은 미검증으로 남긴다.
- `.tres`/텍스처 변경이 실제 PCK에 들어가는지 확인한다. `prepare_godot_project.py`는 `godot/`를 복사하지만 현재 삭제 동기화 대상에는 `.tres`가 없다. 프리셋 파일을 추가/삭제한다면 잔여 프리셋이 패키지에 남지 않도록 해당 suffix의 소스 동기화를 국소 보완한다.
- 별도 외부 텍스처를 도입하는 후속 작업에서는 현재 자산 복사 목록과 export 필터를 확인한다. GLB 내장 텍스처를 다시 파일로 중복 포함하지 않는다. 새 Godot 자산은 PCK 경로를 사용하고 Flutter asset 중복은 만들지 않는다.
- 로컬 APK는 변경 전후 실제 바이트 수·PCK·주요 증감 원인을 기록한다. 네이티브 의존성/ABI는 그대로다. 공개 배포가 별도 요청되면 [APK 용량 점검](android_apk_distribution.md#용량-점검)의 이전 공개본 비교까지 수행한다.

## 10. 산출물과 이후 확장

다음 세션의 결과는 `design/stage1_3d/native_material_workflow/verification/<실험명>/`에 모은다. 비교 이미지마다 Blender / Godot 데스크톱 / Android 본게임 / Android 검수 앱을 구분한다. 결과 문서에는 사용 GLB 해시, 카메라와 프레임 조건, 기존/내장 재질 설정 차이, 시각 판정, 검사 명령과 결과, APK 경로·크기, 성능 측정 조건·미검증 항목을 남긴다. 숫자 동일성·빌드 통과·정지 에뮬레이터 FPS만으로 재질 이관 완료를 선언하지 않는다.

첫 실험이 통과하면 같은 순서로 석재·금속 등 필요한 소재만 확장한다. 앞으로 새 에셋은 **Blender 대표 원본 하나 → 최종 GLB → 엔진 내장 재질·공용 조명 → 실제 게임 크기의 Android 확인 → 같은 소재 에셋 확대** 순서로 제작한다. 엔진에서 확인하지 않은 Blender 완성 이미지를 대량 제작의 기술 보증으로 삼지 않는다.

현재 코어의 시각 이관 미완료 기록은 실제 검증 결과가 나온 뒤 갱신한다. 원본·프리셋·조명 결정이 바뀌면 `DESIGNS.md`의 관련 기준과 제작 README를 함께 수정한다. 채택되지 않은 시도를 현행 구현 지시로 남기지 않는다.

다음 세션에 전달할 요청:

> `docs/stage1_native_material_workflow.md`를 읽고 9절의 1~6단계에 따라 첫 실험을 실행해줘. 현재 GLB 형태와 게임 카메라를 보존한 채 코어의 현재 재질/임포트 내장 재질/내장 굴절 설정을 동일 조건에서 비교하고, 대표 석재·금속과 함께 실제 Android 화면에서 확인해줘. 통과한 내장 재질만 공용 런타임에 채택하고, 비교 캡처·로컬 APK·검증 결과·남은 차이를 남겨줘. 핵심 표현이 부족하면 새 광학 셰이더를 즉시 작성하지 말고 원인과 내장 기능의 한계를 인계해줘. 기존 포탈·식생 바람·포탄 VFX의 전면 교체와 공개 배포는 범위에 포함하지 않아.
