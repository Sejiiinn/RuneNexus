# S26 Ultra 대포 3D APK 끊김 분석

역할: 사용자 체감 보고에 대한 원인 후보와 개선 순서. 확인일: 2026-09-11. 코드·에셋·설치된 렌더 의존성을 읽기 전용으로 대조한 분석이며, 실기기 성능 측정 결과는 아니다. 게임 코드와 APK는 이번 조사에서 변경하지 않았다.

## 판단

사용자가 **“폭발이 없어도 느리다”**고 확인했다. 따라서 최우선 대상은 **기본 장면의 조명·그림자·draw 제출과 네이티브 프레임 처리 경로**다. 폭발 최적화만으로 이 증상을 해결할 수 없다.

현재 네이티브 렌더 경로는 Dart 프레임 안에서 씬 처리·GL 명령 제출·동기 surface 제출을 수행한다. 2048² 그림자와 여러 면광원도 폭발 유무와 무관하게 기본 비용으로 남는다. 기본 장면의 GPU 비용과 CPU/드라이버 제출 대기를 먼저 구분해야 한다. 기기 등급만으로 원인을 판단하거나 엔진 교체를 결정할 근거는 부족하다.

권장 순서는 **빈 3D 화면과 무착탄 전장 비교 → 그림자·재질·제출 비용 분리 → 프레임 주기와 기본 장면 최적화 → 남은 폭발 비용 최적화**다. APK로 바꾸어도 씬 구성과 조명·체적 작업량은 그대로이며, 새로운 네이티브 제출 경로도 검증해야 한다.

## 조사 범위와 확인된 조건

- 대상: `com.example.rune_nexus.preview3d`, ARM64 release APK, SHA-256 `0d3c0d683d2acdd2f636e9072eba99dc045486310496c5547a2bd27f9259b251`. [APK 확인 기록](../../build/apk-preview/verification.json).
- 진입점: [대포 6문 연속 사격 화면](../../design/stage1_3d/cannon_impact/barrage_runtime/main.dart). 실제 전투 로직과 체력 10억의 정지 표적 3기를 사용한다.
- 사용자 표현인 “울트라 26”은 Galaxy S26 Ultra로 해석했다. 정확한 모델·활성 주사율·실행 배속·발열 상태·실제 GL backend는 확인하지 못했다.
- 추가 증상: 폭발이 없는 상태에서도 느림. “그림자가 주원인” 또는 “ANGLE이 주원인”까지 특정한 것은 아니다.
- 현재 연결된 Android 기기가 없어 FPS, GPU 시간, 프레임 지연 분포와 발열 후 저하는 측정하지 못했다. 사용자 요청에 따라 웹 렌더 테스트는 수행하지 않았다.
- 의존성: `three_js_angle_renderer 0.0.1`, `flutter_angle 0.4.2`, `flame 1.37.0`의 설치된 소스를 확인했다.

## 원인 후보와 근거

### 1. 기본 장면의 조명·그림자 — 최우선 분리 대상

[Stage1Scene](../../lib/game/rendering/stage1_3d/stage1_scene.dart)은 면광원 3개, 점광원 4개, 태양 1개, 반구광 1개를 유지한다. 태양 그림자 맵은 **2048×2048**이며 지형·포탑·적이 그림자 생성에 참여한다. renderer와 LightShadow의 `autoUpdate`가 활성화돼 폭발 없이도 매 프레임 그림자를 다시 그린다. 면광원은 PBR 재질에서 LTC 계산을 사용한다.

착탄 점광원은 개수를 고정하고 강도만 변경하므로 광원 수 변화에 따른 셰이더 재컴파일을 피하고 있다. 점광원의 그림자는 켜져 있지 않아 폭발마다 큐브 그림자 맵을 만드는 구조는 아니다. 체적 셰이더도 이 광원들을 전부 계산하지 않고 자체 방향광 차폐를 사용한다.

기본 맵의 타일 80개와 지형 GLB의 메타데이터는 일치한다. 메타데이터가 로더에서 그대로 전달되면 원본 전장 경로를 선택할 조건이며, 이 경로의 기본 에셋 합계는 아래와 같다. 실기기에서 선택된 경로와 실제 draw 수는 아직 기록하지 않았다.

| 대상 | mesh primitive | 삼각형 |
| --- | ---: | ---: |
| 원본 전장 지형 | 7 | 65,624 |
| 포털·코어 | 14 | 3,768 |
| 대포 6문 | 42 | 68,712 |
| 전차 표적 3기 | 6 | 2,877 |
| 합계 | 69 | 140,981 |

이는 상태 표시·VFX를 제외한 에셋상 작업 단위이며 실측 draw call이 아니다. 그림자 패스에서는 caster 기하를 다시 처리한다. 지형이 이미 7 primitive인 경로라면 지형 합치기만으로 큰 이득을 기대하기 어렵다. draw·그림자·재질 시간을 측정하지 않고 폴리곤 수부터 낮추는 것은 우선순위가 낮다.

화질을 유지하며 먼저 정리할 수 있는 CPU 반복 작업도 확인했다.

- 각 PBR 재질의 `onBeforeRender`가 [면광원 방향 보정](../../lib/game/rendering/stage1_3d/stage1_lighting.dart)을 호출한다. 같은 프레임·카메라에서도 광원 배열과 세 면광원의 행렬·벡터 계산을 반복한다. renderer의 `setupLightsView` 이후라는 순서를 보존하면서 렌더 패스·카메라별로 한 번 수행하는 후보가 있다.
- 숨긴 원본 `_library`와 풀 `_pool`도 scene의 자식이다. 패키지의 `Object3D.updateMatrixWorld()`는 가시성 검사 없이 자식을 재귀하므로 이 객체들도 매 프레임 행렬 갱신에 참여한다. 실제 렌더 트리에서 분리하되 재사용·자원 해제 책임을 유지하는 후보가 있다. 현재 패키지는 이 함수에서 `matrixWorldAutoUpdate`를 검사하지 않아 플래그 한 줄로 해결된다고 가정할 수 없다.
- `Mesh.copy()`는 geometry와 material을 실제 복제한다. 일반 Three.js의 공유 복제와 다르다. 다만 생성은 `putIfAbsent`·풀 경로에 있어 매 프레임 복제되는 것은 아니다. 공유 전환은 메모리·업로드 개선 후보이며 자원 수명 검토가 필요하다.

이 반복 비용의 존재는 확인했지만 전체 프레임에서 차지하는 비중은 측정하지 못했다. 포털·코어의 맥동과 적의 미세 움직임도 있으므로 “폭발 없음”을 “장면 전체 정지”로 취급해 그림자를 무조건 고정하면 안 된다.

### 2. 네이티브 렌더 제출·프레임 주기 — 측정 필요

설치된 `three_viewer.dart`의 흐름은 `Ticker → render → renderer.render → angle.updateTexture → animation event`다. Android surface 경로의 `updateTexture()`는 동기 FFI `eglSwapBuffers`를 호출한다. 이 호출에 GPU 또는 버퍼 큐 대기가 생기면 Dart/UI 프레임까지 지연될 가능성이 있다. `await`가 렌더링을 별도 스레드로 옮기지는 않는다. swap 시간이 길어도 앞선 GPU 작업이나 버퍼 소비를 기다릴 수 있으므로 드라이버 결함으로 바로 판정하지 않는다. 동일 surface에서 clear+swap만 수행하는 비교가 구분점이다.

Flame과 ThreeJS는 각각 Ticker를 사용하고 별도 목표 FPS 제한이 없다. 실제 활성 주사율이 높으면 렌더 시도 횟수도 늘어날 수 있다. `_updating` 가드는 있어 프레임 작업이 무제한 중첩되지는 않는다. 60fps 목표라면 전투 배속을 보존하면서 렌더 호출 주기를 일정하게 맞추는 비교가 필요하다.

현재 `syncScene()`은 렌더 제출 이후 animation event에서 실행돼 다음 렌더에 반영된다. 렌더 직전의 기존 `rendererUpdate` 훅을 사용하는 개선 후보가 있지만, 이 한 프레임 순서 문제만으로 심한 지속 끊김을 설명할 수는 없다. 일시 정지 버튼도 Flame만 멈추고 ThreeJS 렌더는 계속한다.

네이티브 구현 근거는 설치 패키지의 `three_js_angle_renderer-0.0.1/lib/three_viewer.dart:229–263`, `flutter_angle-0.4.2/lib/desktop/angle.dart:523–559`다.

### 3. 빈 공간에도 수행되는 폭발별 체적 적분 — 기본 장면 이후

아래는 착탄 때 추가되는 비용이다. 무착탄 상태의 끊김을 설명하는 근거로 사용하지 않는다.

[체적 셰이더](../../lib/game/rendering/stage1_3d/battlefield_impact_effects.dart)의 현재 구조는 다음과 같다.

| 항목 | 코드에서 확인한 사실 | 의미 |
| --- | --- | --- |
| 적분 단계 | 픽셀당 최대 32회, `field()`가 인접 두 시간의 3D 텍스처를 조회 | 주 경로의 `texture()` 호출 상한은 64회 |
| 자체 차폐 | 네 적분 단계 이상 간격으로 추가 `field()`, 최대 8회 | 주 경로와 합쳐 최대 80회/폭발/픽셀 |
| 체적 경계 | 수명 내내 `4.7r × 2.9r × 4.7r` 고정 박스 | 초기 작은 폭발에도 큰 영역을 처리 |
| 빈 밀도 처리 | 텍스처를 조회한 뒤 밀도 `<0.005`이면 다음 단계로 이동 | 빈 공간 조회 자체는 남음 |
| 종료 조건 | 투과율 `<0.015`이면 종료, 최종 알파 `<0.003`이면 버림 | 희박하거나 빈 광선은 루프를 오래 진행할 수 있음 |
| 중첩 | 투명 재질, `depthWrite=false` | 앞 폭발의 불투명도가 뒤 폭발 계산을 종료시키지 못함 |

80회는 GLSL 함수 호출의 이론적 상한이다. 실제 메모리 거래 횟수나 GPU 시간은 분기·선형 필터·캐시·조기 종료에 따라 달라진다. 장면의 불투명 깊이 텍스처로 광선의 종료 지점을 잘라내는 처리도 현재 없다.

최종 `cannon_field.bin`의 밀도 채널을 직접 분석하면 빈 공간을 줄일 여지가 확인된다.

| 캐시 시간 | 밀도가 양수인 격자점 / 전체 110,592개 | 한 복셀 확장한 XZ 경계 면적 / 전체 박스 |
| --- | ---: | ---: |
| 0.008초 | 44개 · 0.040% | 0.91% |
| 0.12초 | 1,142개 · 1.033% | 18.92% |
| 0.34초 | 2,312개 · 2.091% | 39.11% |
| 0.55초 | 1,992개 · 1.801% | 32.82% |

이 표는 회전 전 단일 시간 표본의 데이터 분포다. 화면의 픽셀 점유율이나 GPU 절감률이 아니다. 실제 경계를 만들 때는 인접 두 시간 표본의 합집합, 공간 보간 여유, 폭발별 회전, 별도 수식으로 그리는 반경 0.085의 기폭 섬광을 모두 포함해야 한다. 희박한 연기를 임의의 큰 밀도 임계값으로 잘라내는 방식은 적절하지 않다.

### 4. 첫 착탄과 새로운 동시 개수 — 순간 끊김 후보

캐시 텍스처는 전장 로딩 때 업로드하지만 효과 풀은 비어 있는 상태에서 시작한다. 처음 착탄하거나 이전보다 더 많은 폭발이 겹치면 `_CannonImpactVisual`을 새로 만들고 geometry·material·instance buffer를 준비한다. 이 경로의 최초 GPU 버퍼 준비·셰이더 컴파일이 순간 지연 후보다. 이후 효과는 풀에서 재사용하므로 이것만으로 계속되는 낮은 FPS를 설명할 수는 없다.

## 이미 적용돼 있어 다시 제안할 필요가 없는 것

- **시간별 3D field 공유 캐시:** 48³ 격자 × 32시간, RGBA8 13.5MiB 한 개. 전장 내 폭발이 공유하고 로딩 단계에서 업로드한다. 폭발별 복제가 아니다. 캐시는 수식 비용을 줄였지만 조회 대역폭은 남는다. [Android 텍스처 대역폭 분석](https://developer.android.com/agi/sys-trace/texture-memory-bw).
- **폭발 내부 파편 인스턴싱:** 불티 56개와 금속 파편 34개가 각각 하나의 `InstancedMesh`다. 남은 후보는 폭발 간 배칭과 매 프레임 탄도·행렬 갱신 비용이다.
- **체적 양면 중복 패스 방지:** `forceSinglePass=true`와 앞뒤 면 선택이 적용돼 있다.
- **광원 개수 고정과 효과 풀 재사용:** 지속적인 재생성·재컴파일을 줄이는 구조가 이미 있다. 풀 사전 확보는 별도 후보다.

| 6 | 화면에서 작은 폭발에만 32/24/16단계 적용 | 표본 수 감소. 밴딩·깜빡임·기폭 섬광 누락을 확인하고 전환 경계를 완만하게 처리 |
| 조건부 | 효과 풀 확보·실제 셰이더 사전 준비 | 처음 착탄/동시 개수 증가 구간의 p99 지연이 클 때 적용. 숨겨 둔 객체 생성만으로 컴파일 완료를 가정하지 않음 |
| 조건부 | 폭발 간 배칭, CPU 행렬·GL 제출 횟수 축소 | CPU/명령 제출 구간이 지배적일 때 적용 |

저해상도 체적 합성은 연기·불 같은 완만한 효과에 사용하는 방법이다. 얇은 금속 파편은 기존 해상도를 유지해야 한다. 깊이 경계의 번짐, 가는 연기 손실, 추가 합성 패스와 모바일 타일 메모리 비용을 함께 검증해야 한다. 픽셀 감소율은 전체 게임 FPS 증가율이 아니다. [NVIDIA GPU Gems: High-Speed Screen Particles](https://developer.nvidia.com/gpugems/gpugems3/part-iv-image-effects/chapter-23-high-speed-screen-particles).

체적 경계 개선은 캐시 제작기·메타데이터·로더·체적 셰이더 중심의 변경이다. 체적 전용 해상도 조절은 별도 렌더 타깃·깊이·합성 연결이 필요해 범위가 더 크다. 빈 3D 화면부터 느리거나 draw 제출이 계속 지배적이라면 ANGLE backend·surface 경로를 우선 검토해야 한다. 그래도 해결되지 않을 때 렌더 backend 변경의 비용과 이득을 비교한다.

## 해상도와 설정에서 주의할 실제 제약

현재 앱은 논리 크기 `880×760`에 `screenResolution:1.25`를 지정한다. 이것은 단말 DPR을 대체하며 다시 곱해지지 않는다. Android surface 생성 요청은 **1100×950 = 1,045,000픽셀**이다. `FittedBox`는 표시 크기만 축소한다. 이 수치 자체가 단말의 실제 표시 픽셀보다 과도하다고 단정할 근거는 없다.

`flutter_angle 0.4.2`의 Android `resize()`는 즉시 반환하고 Java resize 구현도 비어 있다. `ThreeJS.setResolution()`은 필드만 변경한다. 따라서 설정을 실행 중 바꾸는 것만으로 실제 surface 해상도가 낮아지지 않는다. 전체 화면 해상도 조절에는 최초 생성 크기 변경 또는 surface 재생성 처리가 필요하다. 체적 전용 렌더 타깃은 이 전체 surface 크기와 구분해 구현해야 한다.

또한 현재 기본 `useSourceTexture=false` 경로는 추가 source texture 복사와 그 경로의 `glFinish()`를 사용하지 않는다. `samples:4` 설정은 현재 생성하지 않는 별도 렌더 타깃용이며, Android surface의 실제 MSAA 적용 여부는 코드 설정만으로 확정할 수 없다. `antialias:false` 한 줄의 개선 효과도 보장할 수 없다.

숨긴 Flame 화면은 `Opacity(0)`에서 페인트가 생략된다. 2D 전장을 완전히 그린 뒤 3D를 다시 그리는 이중 래스터 비용으로 설명하면 부정확하다. 체력 표시의 `setState()`도 초당 4회이며 렌더러·에셋을 매번 재생성하지 않는다.

## 실기기 측정안과 완료 기준

기존 앱과 별도 설치되는 시험 앱에서 동일한 시점·대포 6문·표적 3기를 유지한다. 다음은 후속 구현·측정안이며 이번 조사에서 비교 스위치나 측정용 APK를 만들지는 않았다.

| 비교 | 분리할 비용 |
| --- | --- |
| 같은 Flutter 화면에서 3D texture 갱신 중단 / 빈 3D 화면을 계속 제출 | Flutter 표시와 native clear·surface 제출 비용 |
| 빈 3D 화면 / 지형만 / 무착탄 전장 | 지형·포탑·적의 기본 장면 비용 |
| 무착탄 전장에서 원래 그림자 / 그림자 제외 | 폭발과 무관한 그림자 패스·샘플링 |
| 시뮬레이션을 멈춘 동일 장면에서 매 프레임 그림자 / 첫 프레임 그림자 유지 | 그림자 표시를 유지한 채 재렌더 비용만 분리 |
| 무착탄 전장에서 원래 PBR / 같은 geometry의 무조명 재질 | 면광원·반사·재질 픽셀 비용과 geometry/제출 비용 분리 |
| 사격 없는 장면 / 실제 사격 | 전투·효과의 추가 비용 |
| 실제 전투는 유지하고 체적만 제외 / 전체 표시 | 연기 적분·중첩 |
| 같은 폭발 시점의 고정 경계 / 보수적 경계 | 빈 공간 계산 |
| 전체 해상도 체적 / 0.75배 / 0.5배 | 체적 픽셀 비용과 합성 비용 |
| 원래 렌더 주기 / 목표 60fps | 호출 빈도·프레임 페이싱·발열 |

진단용 효과 제외는 원인을 분리하기 위한 비교이며 제품에서 효과를 숨기는 해결안이 아니다. 같은 상태·효과 나이·실제 활성 폭발 수를 맞춰 비교해야 한다. 4배속은 공격과 효과 수명 양쪽에 적용되므로 평균 동시 폭발 수가 자동으로 네 배가 된다고 계산하지 않는다.

1. 최초 실행에 실제 surface 크기, `GL_VENDOR/GL_RENDERER/GL_VERSION`, EGL 샘플 수, 활성 주사율을 기록한다.
2. Flame update, `syncScene`, renderer CPU 시간, `eglSwapBuffers` 대기, 렌더 호출/건너뛴 Ticker, draw call과 활성 폭발 수를 구분한다. 매 프레임 `glFinish()`를 넣어 측정 조건을 바꾸지 않는다.
3. 물리 기기의 profile 빌드로 CPU를 분석하고 release에서 지속 재생을 확인한다. 첫 착탄과 충분히 준비된 60초 구간, 10분 지속 전투 후 구간을 구분한다. [Flutter 성능 측정 지침](https://docs.flutter.dev/perf/ui-performance).
4. 프레임 시간 p50/p95/p99, 16.7ms 초과 비율, 최장 지연을 기록한다. GPU 시간은 지원되는 기기 도구로 별도 확인한다. Flutter UI/raster 시간만으로 외부 3D 텍스처의 GPU 시간을 단정하지 않는다. AGI의 GLES 경로는 자체 ANGLE 조건이 있으므로 현재 앱의 bundled ANGLE과 호환되는지 먼저 확인한다. [Android GPU Frame Profiler](https://developer.android.com/agi/frame-trace/frame-profiler).
5. 우선 목표는 해당 기기의 1배속·4배속에서 안정적인 60fps다. 평균 FPS만으로 통과시키지 않고 반복적인 긴 프레임과 발열 후 저하를 확인한다. 두 카메라에서 기폭 섬광·가는 연기·금속 파편·깊이 경계가 유지되는지도 함께 확인한다.

현재 단계에서 “몇 배 빨라진다”, “S26 Ultra에서 통과했다”는 결론은 낼 수 없다. 무착탄 상태의 기본 렌더 비용부터 분리하고, 같은 기기의 구간별 측정으로 변경을 결정해야 한다. 폭발 최적화는 그 다음에 추가 부하를 줄이는 단계다.
