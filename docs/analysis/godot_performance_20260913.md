# 현행 Godot 전장 성능 1차 진단

확인일: 2026-09-13. 대상은 현재 작업 트리의 Android 본게임과 Godot Mobile 렌더러다. 사용자가 테스터의 렉을 보고하여 코드·에셋과 기존 APK의 렌더 통계를 조사했다. 게임 코드·에셋·영구 그래픽 설정은 변경하지 않았다. 진단 중 임시로 제외한 그림자·전장은 복원하고 메모리 게임을 종료했다.

## 결론

**2장 반복 타일의 높은 기하 작업량이 가장 먼저 분리할 렌더 후보**다. 10번은 전투를 시작하지 않은 상태에서도 1번보다 약 7.3배의 프리미티브와 5.3배의 드로 콜을 기록했다. 폭발이 없는 준비 화면에서도 남는 비용이다. 별도로 프레임 JSON을 전체 파싱하는 잠금 구간과 동일 표시 위치의 반복 계산을 확인했다. 이 부분들은 외형을 바꾸지 않고 개선할 수 있는 후보다.

이는 테스터 기기의 주원인을 확정한 결과는 아니다. 기기·APK 버전·발생 스테이지·배속·전투 상황은 아직 전달받지 못했으며 연결된 장치는 ARM64 에뮬레이터뿐이다. [이전 S26 분석](s26_ultra_cannon_performance_20260911.md)은 제거된 ThreeJS 경로의 기록이므로 현행 Godot의 원인으로 재사용하지 않았다.

## 실제 렌더 작업량

기존 디버그 APK의 메모리 게임에서 전투 전 고정 시점으로 측정했다. Godot의 기존 `getMetrics`를 읽었으며 새 벤치마크 장면이나 계측용 게임 코드를 추가하지 않았다. 각 조건에서 1초 통계 5개, 10번 기본 조건은 12개를 수집했다.

| 조건 | 프리미티브 / 프레임 | 드로 콜 / 프레임 |
| --- | ---: | ---: |
| 1번 기본 | 139,809 | 36 |
| 10번 기본 | 1,019,108 | 192 |
| 10번 그림자만 제외 | 854,030 | 97 |
| 10번 3D 전장 제외 | 0 | 0 |

이 수치는 엔진의 렌더 통계이며 원본 GLB의 삼각형 수와 동일한 지표가 아니다. 그림자·LOD·컬링 등 실제 렌더 경로의 영향을 받는다. 빈 전장과 그림자 제외는 원인 분리용이며 제품에서 환경이나 그림자를 삭제하자는 제안이 아니다.

[원시 통계](godot_performance_20260913/native_samples.json)와 [요약](godot_performance_20260913/summary.json)을 보존했다. 프레임 간격은 기본 10번 약 37.3ms, 그림자 제외 약 35.2ms, 빈 전장 약 21.2ms, 기본 1번 약 28.9ms였다(1초 평균값들의 중앙값). **에뮬레이터·디버그·공유 호스트 조건의 참고값이며 실기기 FPS, GPU 시간, p95/p99 또는 예상 개선율로 해석하면 안 된다.** 그림자 제외만으로 렉이 해결된다는 결론도 낼 수 없다. `viewport`는 Godot 논리 표시 영역이며 실제 물리 렌더 버퍼 크기로 확인한 값이 아니다.

## 원인 후보와 코드 근거

### 1. 타일 한 칸의 세부 모델을 전장 전체에 반복

`chapter2_tiles.glb`의 원본 삼각형은 길 17,402개, 건설칸 19,382개다. 포탈·코어 아래에도 길 타일이 들어간다. 맵별 원본 LOD 합계는 6번 892,716 / 7번 830,610 / 8번 757,042 / 9번 778,404 / 10번 981,706개다. 실제 화면 통계와 원본 합계는 구분한다.

[타일 제작](../../design/chapter2_3d/tiles/build_tiles.py:170)은 각 돌의 모서리를 세분하고 4단 높이와 베벨을 만든다. [기단 제작](../../design/chapter2_3d/tiles/build_tiles.py:262)은 타일마다 3단×4면×4조각, 즉 측면 석재 48개와 내부 기단을 만든다. 이 모델을 [맵의 각 칸에 반복](../../godot/main.gd:852)한다. 인접 타일 사이로 가려지는 측면까지 원본에 포함돼 있다. [에셋 수치·해시](godot_performance_20260913/asset_workload.json).

우선 비교할 변경은 **보이는 외곽과 틈을 유지하면서 완전히 가려지는 내부 면을 제거하는 전장 출력**, 그리고 실제 게임 크기에서 작은 모서리만 줄이는 LOD다. 큰 실루엣·균열·베벨·노멀·색은 유지해야 한다. 전체 모델을 단순한 판으로 교체하는 방향은 아니다. 화면의 작은 영역에 삼각형이 밀집하는 문제와 LOD의 필요성은 [Godot GPU 최적화 지침](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)에서도 설명한다.

### 2. 매 프레임 전체 JSON 파싱이 스레드 간 잠금 안에 있음

[Android 브리지](../../android/app/src/main/kotlin/com/example/rune_nexus/GodotBridge.kt:29)는 `sceneEpoch` 하나를 읽기 위해 `JSONObject(json)`으로 전체 전투 프레임을 파싱한다. `submitFrame`의 `@Synchronized` 잠금을 Godot의 `take_frame`·`report_presentation`도 사용한다. Godot에서는 받은 JSON을 다시 파싱한다. 따라서 Android UI 쪽 파싱이 Godot 스레드의 접근을 지연할 수 있다. 실제 잠금 대기 시간은 아직 측정하지 않았다.

품질 보존 후보는 epoch를 메시지 외피로 분리하고 잠금 내부에서는 최신 문자열만 교체하는 것이다. 기존 장면 세대·리셋 순서·최신 프레임 슬롯 계약은 유지해야 한다. 이미 최신 슬롯으로 덮어쓰므로 무한 전송 큐가 쌓이는 문제는 아니다.

### 3. 동일 프레임의 표시·직렬화 작업 반복

- [Godot 표시 갱신](../../godot/main.gd:589)은 카메라 업데이트, 프레임 적용 끝, 렌더 직전에서 `_present_overlays`를 반복 호출한다. 적 라벨 투영·위치 갱신 등이 중복된다. 실제 Canvas 그리기 요청은 합쳐질 수 있으므로 draw가 세 배라는 뜻은 아니다.
- [카메라 맞춤](../../godot/main.gd:457)은 맵·시점이 그대로여도 매 수신 프레임에 모든 타일 모서리와 전용 지형 지지점을 투영한다. 변경 조건을 정확히 유지하는 캐시 후보가 있다.
- [Flutter 전송](../../lib/ui/hud/godot_battlefield_view.dart:201)은 프레임 객체·Map/List·JSON을 매번 생성하고, 변하지 않는 맵도 전송한다. 본체와 라벨용 적 상태를 각각 생성하는 부분도 있다. `submitFrame` 뒤 `getPresentation`까지 두 차례 순차 왕복한다. 실제 Godot 렌더 완료를 기다리는 동기 ACK 구조는 아니다.

화질을 건드리지 않는 후보지만, 전체 프레임에서의 비중은 별도 CPU 구간 계측으로 확인해야 한다. HUD를 매 프레임 `setState`하거나 Godot 엔진을 매번 재생성하는 구조라는 근거는 없으며, 전투 통계 publish는 이미 0.2초 간격이다.

### 4. 사격 때 추가되는 비용은 증상에 따라 후속 분리

[착탄 셰이더](../../godot/effects/cannon_impact.gdshader:109)는 최대 32단계 체적 적분을 사용하고, 포구·비행 연기는 각각 16단계다. [착탄 입자](../../godot/effects/godot_impact.gd:126)는 효과마다 불티 56개·파편 34개의 위치를 CPU에서 갱신한다. 풀과 캐시 공유는 이미 구현돼 있다.

이번 준비 화면 측정에는 사격이 없으므로 이 효과를 현재 지연의 확정 원인으로 쓰지 않는다. 테스터 증상이 대포·다중 발사 구간이면 동일 전투 상태에서 체적 비용과 CPU 갱신을 분리해야 한다. 보상 선택 때만 느리면 [선택 마스크의 별도 3D 패스](../../godot/ui/battlefield_selection.gd:282)를 확인한다.

## 다음 판단에 필요한 정보

테스터 기기 모델, 사용한 APK 버전, 스테이지와 배속, 적·포탑이 적을 때도 느린지 또는 특정 효과 때만 끊기는지가 필요하다. 해당 조건의 profile/release 실기기에서 CPU 구간·GPU 시간·프레임 지연을 분리해야 최종 주원인을 확정할 수 있다. Godot의 기존 평균/max 프레임 간격은 CPU/GPU 실행 시간 측정이 아니다. 필요 시 [렌더 시간 계측 API](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver-method-viewport-set-measure-render-time)를 사용한다.

현재 조사에서 우선순위는 **2장 타일의 보이지 않는 기하 비용 → 외형과 무관한 프레임 중복·잠금 → 보고된 전투 상황의 효과 비용**이다. 모바일에서 반드시 화질부터 낮춰야 한다는 결론은 나오지 않았다.
