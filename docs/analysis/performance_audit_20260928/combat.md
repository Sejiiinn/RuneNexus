# 전투 CPU 읽기 전용 점검

2026-09-28. 구현·에셋 변경 없음. 기존 shared stats와 저장 capture 개선은 제외했다. 소스 확인과 임시 프로젝트의 Godot 4.7.2 headless 합성 실행만 수행했다. 아래 시간은 전투 함수의 데스크톱 CPU 시간이며 실제 앱 프레임, GPU, A34 성능이 아니다.

## 우선순위 1: 지속 피해 이벤트가 경제 수집 전체 경로를 매 프레임 깨움

- 발생 경로: `godot/combat/native_enemy_state.gd:208` `_dot_hit()` → 같은 파일 `:216` 매 실제 피해마다 damage 이벤트 → `native_combat_runtime.gd:793` `_collect()`의 deep copy와 `:850` `_emit()` → `godot/session/session_controller.gd:239` 새 이벤트가 있으면 `command()` → `run_session.gd:99` progression deep copy·퀘스트 갱신.
- 화상/독 피해는 매 step 적용되고, 경제 수집의 match(`run_session.gd:113`)는 kill / waveCompleted / coreDefeated만 처리한다. damage·damageNumber는 경제 처리 없이 ACK만 전진시킨다. 포탑 화상 누적 피해 집계는 이미 runtime `_collect()`에서 처리한다.
- 합성 실측: 포탑 0, 적 40, dt=1/60, 60 step, 적당 10초·DPS1 화상, 충분한 HP. **damage 2,400개 + damageNumber 120개**. 각 step마다 새 이벤트가 발생한다. 이벤트 배열은 각 step 후 지워 ACK 후 잔류량을 모사했다. 전투만 step 평균 무화상 **78.7μs**, 화상 **691.4μs**. 경제 collect 및 UI 비용은 이 시간에 포함하지 않았다.
- 소비자 확인: raw `runtime.events`를 직접 읽는 현재 코드에는 경제 collect와 guardian_preview가 있으며 후자는 kill만 처리한다(`guardian_preview.gd:179`). battlefield_effects의 damage 표시는 별도 presentation/visual_effects 경로(`native_combat_runtime.gd:954`)다. snapshot·ACK 및 미정산 이벤트 저장 거부 계약도 있으므로 무조건 이벤트를 지우는 변경은 제안하지 않는다.
- 수정 방향: 경제 변경이 없는 이벤트 묶음은 저렴하게 ACK하고, 실제 경제/진행 변경이 필요할 때만 progression 복사·퀘스트 갱신을 수행. 플레이 시간 누적·종료·킬 순서·화상 누적/코어 보너스 피해·저장 전 ACK를 유지해야 한다. 이벤트 journal 분리는 추가 설계가 필요하다.
- 기존 최적화: 화상 출처 포탑 검색은 이미 step-local 좌표 인덱스(`native_combat_runtime.gd:780`)를 사용한다. 이를 다시 최적화 후보로 제안하지 않는다.

정정: 아래 전체 적 탐색을 우선순위 2 병목으로 제시했던 판단은 철회한다. 전체 순회 자체는 결함이 아니며, 적 수십 개에서는 공간 인덱스 관리보다 저렴할 수 있다. 2.571ms는 표적 탐색만이 아니라 합성 조건의 전투 step 전체 시간이다. 실제 탐색 구간과 대안 비용을 비교하기 전에는 수정 필요성을 확정하지 않는다.

후속: 피해 이벤트 수집의 깊은 복사 축소는 [별도 구현·검증 기록](../damage_event_collection_20260928/README.md)에 남겼다. 아래 수치는 변경 전 조사 당시 결과다.

## 추가 측정 후보: 사거리 안 적이 없는 포탑의 매 프레임 전체 적 검색

- 발생 경로: `native_combat_runtime.gd:460` `_finish_step()` → 모든 포탑 `_tick_turret()` → cooldown=0이고 표적이 없으면 `:509` `_target()` → `:556` `enemies.values()` 전체 순회. 실패한 탐색은 cooldown을 설정하지 않으므로 동일 포탑이 다음 frame에 다시 전체 탐색한다.
- 복잡도: 사거리 밖 대기 포탑 T개·적 E개에서 매 frame O(T×E), 호출마다 values 배열도 생성한다. 성공한 일반 포탑은 cooldown 중 검색을 생략하고, 저격은 기존 조준 대상을 유지한다. 모든 포탑이 언제나 매 프레임 검색한다는 뜻은 아니다.
- 합성 실측: 포탑 24, 정지 적 40을 모두 사거리 밖에 놓고 60 step 실행. **_target 1,440회 / 적 후보 57,600회 방문**. 전투 step 평균 **2,571.2μs**. 같은 포탑 24·적0은 **162.3μs**였다. 대상 획득 실패 검색을 분리한 배치이며 실제 스테이지 분포를 측정한 값은 아니다.
- 현재 콘텐츠 규모 확인: 전체 카탈로그 최대 건설칸 32개(stage1), 한 웨이브 최대 spawn 40개(stage10 round35). 24×40은 수만 개 객체를 만든 스트레스 시험이지만은 않다. 동시에 전부 사거리 밖이라는 조건은 합성이다.
- 기존 최적화: 투사체 충돌은 이미 spatial broadphase(`:589`)를 사용한다(투사체8개 이상·적32개 이상). 이 인덱스는 포탑 tick 이후 만들어지며 `_target`, 냉각 범위 공격(`:535`), 폭발 범위 검색(`:709`)에는 적용되지 않는다. 모든 투사체가 전체 scan이라는 제안은 잘못이다.
- 수정 방향: 적 이동 완료 후 한 번 만든 공간 인덱스를 표적/범위 질의에도 공유하는 후보를 측정. 작은 수에서는 현재 선형 검색 유지. body 반경·동점 insertion order·죽은 적 제외·연쇄 제외 목록을 보존해야 한다. 단순 재탐색 타이머는 최초 공격 지연을 바꾸므로 그대로 적용하지 않는다.

## 우선순위 3: 폭발 대상 구분에 큰 Dictionary 값 비교

- `native_combat_runtime.gd:710`의 `e != target`, `:714`의 `e == target`은 ID/동일 객체 구분에 전체 Dictionary 비교를 사용한다. 동일 타입 적은 앞쪽 여러 필드가 같아서 key 비교 비용이 발생한다.
- 별도 미세 측정: 실제 `Catalog.enemy→Enemy.create`로 만든 61키 적 40개, 80,000번 비교. Dictionary 비교 **93,032μs**, ID 비교 **15,630μs**, `is_same` 비교 **9,891μs**. 세 경우 모두 비대상 수 78,000으로 일치했다. 이것은 비교 연산만의 합성 시간이며 폭발 전체 속도 개선 배수가 아니다.
- 수정 방향: 엔티티 ID 또는 객체 identity로 구분. 직접 대상 제외·피해 계수 계약을 확인하면 국소 변경이 가능하다. 빈번한 다중탄 폭발에서 누적될 수 있지만, 1·2번보다 작은 후보로 분류한다.

## 실행 범위와 한계

임시 프로젝트에 현행 combat/content 스크립트를 복사하고 Runtime 하위 클래스에서 `_target`과 `_emit` 횟수만 계측했다. 원래 메서드를 호출했고 생산 코드에는 계측을 넣지 않았다. 탐색 시험의 적은 x/y 약100, 빈 이동 경로, 포탑은 원점에 배치해 이동/명중 영향을 배제했다. 적 dictionary 비교 시험도 동일 합성 객체를 사용했다. 단일 짧은 실행이므로 시간은 후보 선별 근거이고 성능 개선 보증이 아니다. 실제 앱/기기 병목 순위를 확정하려면 대표 웨이브의 분리 프로파일이 필요하다.

추가로 정규화 기본 진행 상태의 `RunSession.collect()`를 별도 계측하려 했으나 임시 하네스가 30초 안에 종료하지 않아 측정을 완료하지 못했다. 위 이벤트 수와 전투 step 계측은 성공한 별도 실행의 값이며, 경제 collect의 CPU 시간은 미측정으로 남긴다. 추가 실험이나 코드 변경은 하지 않았다.
