# 모바일 다중 포탄 폭발 최적화 조사

역할: 2026-09-11 Astra 병렬 조사와 채택한 우선안의 구현 기록. 시간별 3D field 캐시와 폭발 내부 파편 인스턴싱은 구현했고, 저해상도 합성·적분 LOD·폭발 간 배칭은 미구현 후보다. 모바일 성능 통과 기록은 아니다. 배포한 별도 APK의 후속 분석은 [S26 Ultra 끊김 분석](s26_ultra_cannon_performance_20260911.md)을 참조한다.

## 결론

시간별 3D 밀도·발광·열도장을 미리 계산해 모든 폭발이 공유하고, 카메라에 따른 광선 적분은 실시간으로 유지하도록 구현했다. 기존 32³ 난류 입력만 캐시하던 방식의 분출 열 방향·밀도 수식 반복을 제작 단계로 옮겼다. 완성 화면을 저장하는 방식은 현재의 angled/drone 시점·입체성 요구와 맞지 않는다.

브라우저 수치는 모바일 수용 기준에서 제외한다. 지원 하한 기종은 아직 미정이다. 현재 연결 기기는 macOS와 Chrome뿐이다. Android SDK·Java·라이선스는 준비됐지만 모바일 실측은 수행하지 못했다. iOS 빌드 환경은 Xcode·CocoaPods 준비가 추가로 필요하다.

폭발 개수를 임의로 숨기거나 금속 파편을 저해상도로 합성하는 것을 기본안으로 삼지 않는다. 저해상도 체적 합성의 이득은 해당 패스의 픽셀 수에 대한 것이며 게임 전체 성능이 네 배가 된다는 뜻은 아니다. [NVIDIA GPU Gems: High-Speed Screen Particles](https://developer.nvidia.com/gpugems/gpugems3/part-iv-image-effects/chapter-23-high-speed-screen-particles)

## 우선안의 변경 범위

- `_CannonImpactVisual`의 위치·카메라 광선·박스·파편·풀 구조를 유지하고 `field()`를 두 시간 표본 사이의 3D 조회 보간으로 교체한다.
- field 출력은 밀도·발광·열도 세 값이다. RGBA8의 RG 두 바이트에 밀도를 16비트로, B에 발광, A에 열도를 저장한다. 공간·시간 보간 후 밀도를 선형 복호화해 희박한 끝의 양자화 손실을 줄인다.
- RGBA8 32³×32시점은 4MiB, 48³×32는 13.5MiB, 64³×32는 32MiB다. 패딩·밉맵·CPU 사본을 제외한 산정이다. 현재는 48³×32를 4×4×2 brick으로 배치한 192×192×96 단일 텍스처(13.5MiB)를 사용한다. 각 brick의 복셀 중심 범위 안에서 보간해 다른 시점 누출을 막는다. 폭발별로 복제하지 않고 전장 단위로 공유한다.
- 데이터는 제작 단계에서 생성하고 전장 로딩 중 업로드해 첫 착탄 때의 생성·업로드 지연을 피한다. 원본 생성 절차는 `design/`, 최종 게임 데이터는 기존 게임 에셋 경로에 둔다.
- 초기 그림자는 캐시된 밀도를 현재 광원 방향에서 추가 조회한다. 빛 차폐까지 굽는 것은 `uAngle`과 광원 방향 관계를 별도로 보존해야 하므로 후순위다.
- 현재 반경 0.085·0.055초의 기폭 섬광은 작은 격자와 균일 시간 표본으로 손실될 수 있다. 섬광은 기존 작은 수식으로 남기고 초기 화염에는 시간 표본을 더 조밀하게 배치한다.
- 현행은 난류를 계산한 뒤 방향을 회전하므로 canonical field 전체를 회전하면 세부 난류 배치는 달라질 수 있다. 초기 화염·회색 흙먼지·가늘게 풀리는 끝·두 시점 입체감을 확인해야 한다.

조회 캐시가 연산량을 줄여도 대역폭 병목으로 바뀔 수 있으므로 개선 폭을 사전에 보장하지 않는다. [Android: Texture Memory Bandwidth](https://developer.android.com/agi/sys-trace/texture-memory-bw)

## 현재 코드와 모바일 검증 준비

`RuneNexusGame.update`는 전투와 이펙트 수명 모두에 배속을 적용한다. 4배속에서 평균 동시 개수가 기계적으로 네 배가 되지는 않는다. 여러 포탑·다중 탄환의 동시 착탄, 프레임당 생성·회수, 겹친 화면 면적을 별도 기록해야 한다.

네이티브 경로는 ThreeJS/ANGLE 렌더 후 Flutter 텍스처를 제출한다. 현재 `useSourceTexture` 기본값은 false이며 추가 소스 텍스처 복사 경로의 `glFinish`를 현재 병목으로 단정할 근거는 없다. 해당 의존성은 수정하지 않았다.

일반 앱의 시험 진입은 debug flag와 URL query를 함께 요구한다. 모바일 측정에는 저장을 건드리지 않는 기존 `Stage1ThreeDPreviewApp`을 직접 실행하는 `design/stage1_3d/mobile_profile/main.dart`를 추가했다. 기존 `shell_runtime/main.dart`는 단일 착탄 외형 검수용이며 실제 4배속 다중 포탑 전투 검증을 대신하지 않는다.

## 실기기 수용 조건

1. 최소 지원 Android 기기와 대표 중급기에서 동일한 실제 전투를 1배속·4배속으로 재현한다.
2. 포탑 수·실제 동시 폭발 수·중첩 면적을 기록하고 초기 셰이더 준비 시점과 충분히 가열된 지속 전투를 구분한다.
3. Flutter profile로 CPU 병목을 찾고 release에서 지속 실행한다. 목표는 60fps이며 프레임 시간 p50/p95/p99·최장 지연·GPU 시간·메모리·발열 후 저하를 보고한다.
4. Flutter 프레임 시간만으로 별도 3D 패스의 GPU 시간을 단정하지 않는다. 기기·API가 지원하는 AGI 또는 GPU 제조사 도구로 체적 패스와 텍스처 비용을 확인한다.
5. 같은 시점의 두 카메라, 작은 효과와 겹친 효과에서 가는 꼬리 소실·깜빡임·합성 경계를 확인한다.

측정 절차 근거: [Flutter UI performance](https://docs.flutter.dev/perf/ui-performance), [Android GPU frame profiler](https://developer.android.com/agi/frame-trace/frame-profiler).
