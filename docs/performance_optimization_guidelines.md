# 성능 최적화 지침

역할: 성능 개선과 반복적인 표시 작업을 구현할 때 사용하는 현행 판단 기준. 확인: 2026-09-14.
적용 범위: Flutter 전투·HUD, Godot 표시, 두 엔진 사이의 전달, 자산 로딩·메모리·APK 크기.
특정 후속 최적화나 엔진 이관을 승인하는 문서는 아니다. 기능별 시간·저장·API 계약과 [디자인 기준](../DESIGNS.md)을 함께 따른다.

## 판단 순서

1. **느린 조건과 비용을 구체화한다.** 어떤 화면·기기·전투 상태에서 끊기는지 확인하고 CPU 계산, GPU 렌더, 엔진 사이 전달·대기, 로딩·할당을 나눈다. 코드에 비싼 연산이 있다는 사실과 실제 주 병목이라는 결론을 구분한다.
2. **현재 구현을 먼저 확인한다.** 이미 적용된 풀·공유 자원·일괄 그리기·가림 처리·광원 제한을 다시 제안하지 않는다. 초기 생성 비용과 매 프레임 비용도 구분한다.
3. **반복 작업을 줄일 수 있는지 확인한다.** 변하지 않는 데이터는 한 번 준비하고 공유한다. 중복 변환·계산·전달·자원 생성을 제거할 수 있는지 검토한 뒤 CPU/GPU 분배를 결정한다.
4. **요청 범위에서 검증 가능한 변경을 적용한다.** 유지할 외형·시간·전투 계약과 비교할 조건을 정하고, 변경 효과를 구분할 수 있는 단위로 비교한다. 실기기가 없으면 가능한 구현·계약·화면 검증을 진행하고 미측정 범위를 남긴다.
5. **확인한 범위까지만 결론 낸다.** 국소 비용 감소와 전체 앱 성능 향상을 구분한다. 관련 검사와 요청한 결과가 확인되면 종료하며, 근거 없이 새 최적화 범위를 계속 늘리지 않는다.

## CPU와 GPU의 작업 분배

GPU는 동일한 계산을 많은 대상에 독립적으로 적용하고, 결과를 GPU에서 바로 소비할 때 좋은 후보가 된다. GPU로 옮기는 것 자체를 목표로 삼지 않는다.

| 작업의 성격 | 우선 검토할 방향 | 확인할 비용·제약 |
| --- | --- | --- |
| 불티·파편·식생 흔들림처럼 초기값과 시간으로 정해지는 반복적인 시각 운동 | GPU에서 위치·회전·변형 계산 | 정점 수, 반복 연산·텍스처 읽기, 외부 전투 시계, 가림 경계 |
| 많은 대상의 지속적인 입자 상태 갱신 | GPUParticles 또는 compute 후보 비교 | 입자당 처리량, 초기화·재시작·재사용, 시뮬레이션 순서, 대상 렌더러·기기 지원 |
| 명중·피해·사망·보상·저장처럼 다음 게임 판단에 결과가 필요한 작업 | 현재 CPU의 전투·저장 책임 유지, 자료구조·중복 계산부터 개선 | GPU 결과 회수·동기화 대기, 처리 순서·정확성, 기존 책임 경계 |
| 수가 적거나 분기가 많고 서로 의존하는 작업 | CPU 처리와 실제 비용부터 확인 | GPU 준비·전달 비용이 계산 절감보다 클 수 있음 |
| 연기·화염 광선 적분, 그림자, 겹친 투명 효과 | 기존 GPU 작업량 자체를 줄이는 후보 비교 | 화면 점유·중첩·샘플 수·해상도·메모리 대역폭과 외형 변화 |

전투 판정도 충분한 규모와 별도 설계가 있으면 GPU 계산을 검토할 수 있다. 다만 현재 표시 최적화 요청을 전투·저장 구조 이관의 승인으로 해석하지 않는다. GPU 결과를 CPU가 즉시 기다려야 하면 동기화가 새 병목이 될 수 있다. [Godot compute 문서](https://docs.godotengine.org/en/stable/tutorials/shaders/compute_shaders.html)

CPU에서 제거한 작업은 GPU에서 실행될 작업이다. GPU가 이미 한계에 가까우면 CPU 비용이 크게 줄어도 전체 프레임 시간은 줄지 않거나 늘 수 있다. 두 처리 시간을 단순 합산하거나 CPU 개선율을 FPS 개선율로 바꾸지 않는다. [Godot 일반 최적화 문서](https://docs.godotengine.org/en/stable/tutorials/performance/general_optimization.html)

## 반복적인 시각 운동을 옮길 때

- **기존 일괄 그리기를 보존한다.** MultiMesh로 묶인 입자를 개별 노드·드로 콜로 풀지 않는다. MultiMesh는 그리기 제출을 묶지만, 입자 운동을 CPU에서 매번 계산하는 비용까지 자동으로 없애지는 않는다.
- **정적 데이터와 동적 상태를 분리한다.** 초기 위치·속도·난수·메시·변하지 않는 매개변수는 재사용한다. 효과마다 다른 시간·반경·방향은 서로 덮어쓰지 않도록 관리하고 필요한 값만 전달한다. 풀 크기를 무조건 크게 잡거나 효과마다 동일 자원을 복제하지 않는다.
- **정점 셰이더와 입자 계산의 단위를 구분한다.** 정점 셰이더의 운동 계산은 입자당 한 번이 아니라 정점마다 반복된다. 메시가 복잡하면 입자 갱신 단계에서 변환을 계산하는 방식과 비교한다. CPU 코드가 줄었다는 이유만으로 GPU 구현이 더 가볍다고 단정하지 않는다.
- **전투 시계를 보존한다.** 전투 상태에 종속된 효과는 정지·배속·재연결·재사용 계약을 따른다. 절대 나이로 재현되는 효과에는 초기값과 외부 나이로 계산하는 방식을 우선 검토한다. 누적 시뮬레이션이 필요한 효과는 정지·재시작·시간 이동 시의 처리도 정의한다. 카메라 이동이 효과의 나이를 진행시키지 않게 한다.
- **외형과 수학을 함께 검증한다.** 입자 수·분포·메시·색·재질·탄도·회전·수명·지형 가림을 유지한다. float 정밀도, 회전 순서, quaternion 정규화, 비균일 스케일의 법선 처리가 기존 출력과 같은지 확인한다. 수식 검사와 실제 GPU 화면 확인은 서로 대체하지 않는다.
- **변형 후 경계를 유지한다.** GPU에서 움직인 위치를 CPU가 모를 수 있으므로 실제 전체 탄도를 포함하는 AABB 등 가림 경계를 제공한다. 카메라 전환·화면 가장자리·효과 종료와 재사용에서 잘림이나 잔류가 없는지 확인한다.

## 측정과 완료 판정

측정은 변경 영향과 사용자 요청에 맞춘다. 실행·캡처 절차는 [인앱 검증](../.agents/in_app_test_guide.md)을 사용하며, 이 문서에 별도 실행 경로를 만들지 않는다.

| 확인하려는 결과 | 필요한 근거 | 해석의 한계 |
| --- | --- | --- |
| 특정 함수의 CPU 비용 감소 | 동일 입력·횟수의 전후 호출 시간 | headless·분리 검사는 GPU 렌더나 전체 FPS를 측정하지 않음 |
| 실제 프레임 지연 감소 | 같은 전투 조건의 프레임 시간·p95/p99·순간 지연과 가능한 CPU/GPU 통계 | Flutter raster, Godot 렌더 CPU, 실제 GPU 시간은 서로 다른 지표 |
| 모바일 체감·지속 성능 | 대상 실기기의 profile/release 실행, 필요한 지속 부하·발열 관찰 | 데스크톱·debug·에뮬레이터 결과로 실기기 개선을 확정하지 않음 |
| 메모리·로딩·배포 크기 감소 | 해당 메모리·로딩 시간·실제 APK/PCK 크기 비교 | 파일 압축률·폴리곤 수·디스크 중복 감소가 곧 프레임 개선은 아님 |

- 같은 기기·빌드 모드·해상도·시점·그래픽 설정·포탑/적 배치·배속을 맞춘다. 셰이더 첫 컴파일·로딩과 반복 전투 비용을 구분하고, 불필요한 동시 빌드·렌더·화면 녹화가 성능 측정에 섞이지 않게 한다. 녹화는 시각 증빙용으로 분리한다.
- 폭발 부하는 동시 개수뿐 아니라 화면 점유와 겹침도 기록한다. 같은 개수의 분산 배치·겹친 배치를 비교하면 중첩 비용을 구분하는 데 도움이 된다. 4배속은 생성과 수명에 함께 적용되므로 평균 동시 효과 수가 자동으로 4배가 된다고 가정하지 않는다.
- 측정 API가 미지원이거나 값을 제공하지 않으면 **미측정**으로 쓴다. GPU 시간이 0으로 반환됐다는 이유로 GPU 비용이 없다고 해석하지 않는다.
- 비교가 흔들리면 순서를 교대하거나 필요한 횟수만 반복한다. 새 변경·실패·미해결 위험이 없으면 통과한 검사를 반복하거나 검증 도구를 확대하지 않는다.
- 개선 보고에는 대상 작업·측정 환경·비교 조건·결과·미측정 범위를 남긴다. 예를 들어 “입자 CPU 갱신 비용 감소”를 “폭발 전체 렉 감소”로 바꾸지 않는다. 외형이나 동작이 실패한 후보는 채택하지 않는다.

## 사례와 근거 활용

기법을 추천할 때 실제 소스에서 무엇을 하는지 확인한다. 공식 문서의 가능 여부, 공개 프로젝트의 채택, 작성자의 성능 주장, 우리 게임의 측정 결과를 구분한다. 가능하면 파일·커밋 링크를 남기고 데모·애드온·배포 게임의 성격도 밝힌다. 다른 프로젝트의 개선 배수를 우리 게임에 적용하지 않는다.

- **우리 게임의 적용 사례:** [대포 입자 GPU 운동 전환](../design/stage1_3d/cannon_impact/gpu_motion/README.md). 기존 두 MultiMesh를 유지하고 정적 초기값과 외부 시간으로 정점 운동을 계산한다. 검사·CPU 분리 측정·Android 화면·실기기 미측정 범위는 해당 기록을 기준으로 한다.
- **엔진 간 성능 지표를 구분한 사례:** [Godot 최적화 전후 비교](analysis/godot_optimization_20260913.md). Godot 지표와 Flutter 합성 및 전체 앱 결과를 함께 확인한다.
- **GPU 입자 채택 근거:** [Godot 공식 TPS 데모](https://github.com/godotengine/tps-demo/blob/a82f15448e9b015440d3bbdf5e10801b260c4e9f/player/bullet/bullet.tscn#L564-L575)의 3D 불티, [Thrive 배포 버전의 폭발 초기화](https://github.com/Revolutionary-Games/Thrive/blob/d397ffdf603c7aa57acc23512450b6db30a5b810/src/microbe_stage/systems/CellBurstEffectSystem.cs#L31-L57). GPU에서 입자 운동을 처리하는 근거이며 우리 정점 셰이더 구현의 속도 보증은 아니다.
- **공식 판단 자료:** [GPU 최적화](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html), [MultiMesh 최적화](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html). 대상 엔진 버전·렌더러·모바일 드라이버에서 실제로 지원되는지 적용 시 확인한다.

일반 판단 기준이 바뀌면 이 문서를 갱신한다. 기능별 측정 수치·원본 캡처·배포 여부는 해당 기록에 두고, 특정 후보가 문서에 소개됐다는 이유로 구현 범위를 자동 확대하지 않는다.
