# Rune Nexus 데모 앱 작업 계획서

마지막 갱신 기준: `main` 브랜치 커밋 `f80749a`.

## 문서 역할

이 문서는 Rune Nexus 데모의 목적, 범위, 단계별 로드맵을 정리한다.

현재 구현 상태와 세부 수치는 다음 문서로 분리한다.

- 구현 완료 여부: `docs/implementation_status.md`
- 현재 전투 규칙과 밸런스 수치: `docs/gameplay_balance_reference.md`
- 다음 작업 우선순위: `docs/next_work_priorities.md`

기존 계획서는 현재 규칙, 밸런스, 일정, 리스크가 한 파일에 함께 들어 있어 갱신 부담이 컸다. 이 문서는 변동이 적은 계획 기준만 남기고, 수시로 바뀌는 전투 수치는 별도 기준 문서로 분리했다.

## 1. 목적

Rune Nexus 데모의 목적은 모바일 세로 화면에서 로그라이트 타워 디펜스의 핵심 루프가 성립하는지 검증하는 것이다.

핵심 검증 질문:

- 포탑에 젬을 연결하는 선택이 직관적인가
- 라운드 종료 후 젬 3개 중 1개를 고르는 선택이 의미 있는가
- 골드를 포탑 구매, 레벨업, 링크 확장 중 어디에 쓸지 고민되는가
- 같은 포탑도 젬 조합에 따라 다른 전투 역할을 갖는가
- 실패 후 룬 보상과 영구 업그레이드가 다음 런을 유도하는가

## 2. 현재 데모 범위

포함된 핵심 범위:

- Flutter + Flame 기반 모바일 세로 화면
- 8 x 10 단일 Grid 맵
- 50라운드 생존형 웨이브
- 스테이지 1~5 선택, 잠금/해금, 스테이지별 기록
- 포탑 5종
- 적 4종
- 젬 12종
- 포탑 레벨업, 2링크/3링크 확장, 젬 장착/해제
- 전투 중 포탑 설치, 레벨업, 링크 확장, 환불
- 라운드 보상 젬 선택
- 로컬 저장과 전투 중 복구
- 결과 화면, 룬 보상, 영구 업그레이드 기초
- 한국어/영어 문구 구조
- Flutter Web 빌드 검증

명시적으로 제외하거나 보류한 범위:

- 젬 희귀도
- 젬 제거 비용
- 동료 성장
- 상점, 광고, 배틀패스, BM
- 실시간 길찾기
- 자유 길막
- 온라인 저장 실제 연동
- 스테이지별 고유 맵/웨이브 완성
- 픽셀 스프라이트 완성 에셋
- 사운드/효과음

## 3. 콘텐츠 방향

### 맵

초기 데모는 단일 맵으로 구성한다.

- 화면 방향: 세로
- Grid 크기: 8 x 10
- 경로 형태: 단일 입구 S자형 경로
- 타일 종류:
  - Path
  - Build
  - Blocked
  - Spawn
  - Core

스테이지 2~5는 현재 같은 맵을 사용한다. 이후 차별화 작업에서 맵, 적 구성, 보상, 시작 조건 중 최소 하나를 다르게 만드는 것이 목표다.

### 포탑

현재 포탑 역할:

| 포탑 | 역할 |
| --- | --- |
| 기관총 | 빠른 단일 물리 공격, 경량화기 젬과 궁합 |
| 대포 | 느린 범위 물리 공격, 폭발/중화기 젬과 궁합 |
| 화염 | 마법 피해와 짧은 화상 지속피해, 지속피해/연쇄 젬과 궁합 |

### 적

현재 적 역할:

| 적 | 역할 |
| --- | --- |
| 일반 | 기본 기준 적 |
| 빠름 | 경량화기 대응 가치를 검증 |
| 탱커 | 레벨업, 대포, 중화기 가치를 검증 |
| 보스 | 10라운드 단위 장기 생존 압박 |

### 젬

젬은 포탑의 최종 역할이 바뀌는 느낌을 주는 것이 목적이다.

현재 젬 목록:

- 가속
- 사거리
- 물리 피해 증폭
- 마법 피해 증폭
- 경량화기 증폭
- 중화기 증폭
- 지속피해 증폭
- 폭발
- 연쇄
- 급소
- 조준경
- 위력 증폭

용어 기준:

- `증가`: 합연산 보너스
- `증폭`: 곱연산 배율 보너스

## 4. 구현 단계 기준

초기 구현 단계는 아래 순서로 잡았다.

1. Flutter + Flame 프로젝트 기반 세팅
2. Grid 맵 렌더링
3. 적 이동
4. 포탑 배치
5. 자동 타겟팅과 공격
6. 웨이브와 라운드
7. 젬 보상 UI
8. 링크와 젬 장착
9. 젬 효과 구현
10. 포탑 성장
11. 승패, 저장, 결과 화면
12. 데모 폴리싱

현재는 1~11단계의 핵심 구현이 완료되어 있고, 12단계와 콘텐츠 확장 작업이 남아 있다.

## 5. 다음 마일스톤

현재 다음 마일스톤은 "스테이지 차별화와 반복 성장 루프 강화"로 본다.

포함 후보:

- 스테이지 2~5의 맵, 웨이브, 보상, 시작 조건 차별화
- 영구 업그레이드 후보 확장
- 영구 업그레이드 해금 단계 구조 검토
- 50라운드 기준 보상과 난이도 곡선 재검토
- 보스 웨이브 체감과 시각적 연출 개선
- 실제 모바일/웹 QA

## 6. UX 원칙

- 전투 중 조작은 빠르고 명확해야 한다.
- 포탑 선택 시 사거리와 선택 테두리를 즉시 확인할 수 있어야 한다.
- 젬 장착/해제는 준비 단계에서만 허용해 전투 중 조작 복잡도를 낮춘다.
- 전투 중 포탑 설치, 레벨업, 링크 확장, 환불은 허용한다.
- 환불은 확인 팝업을 거쳐야 한다.
- 라운드 예고와 적 미리보기는 실제 전투 수치와 일치해야 한다.
- 결과 화면은 도달 라운드, 신기록, 신규 해금, 획득 룬, 다음 행동을 분명히 보여야 한다.
- 작은 모바일 화면에서 긴 설명문은 피한다.

## 7. 그래픽과 연출 방향

데모에서는 완성 에셋보다 가독성과 전투 피드백을 우선한다.

우선순위:

- 포탑, 적, 투사체가 작은 화면에서도 구분될 것
- 선택한 포탑과 사거리가 눈에 띌 것
- 폭발, 연쇄, 화상 효과가 젬 효과로 인식될 것
- 보스 등장과 처치가 일반 웨이브와 구분될 것

보류:

- 고급 픽셀 아트
- 사운드/효과음
- 복잡한 보스 전용 패턴

## 8. 리스크와 대응

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| `RuneNexusGame` 책임 증가 | 변경 충돌과 회귀 위험 증가 | 기능 확장 후 저장/선택/전투 책임을 작은 단위로 분리 |
| 젬 효과 하드코딩 증가 | 확장 어려움 | 새 젬 추가 전 효과 타입과 장착 규칙을 먼저 점검 |
| 밸런스 수치가 문서와 코드에서 어긋남 | 판단 기준 혼선 | 수치 문서는 `gameplay_balance_reference.md`로 집중 |
| 모바일 화면 정보 과밀 | 조작 피로도 증가 | 하단 패널 정보량 제한, 선택 상태 강조 |
| Web 캐시 | 최신 빌드 확인 혼선 | 개발 빌드는 `--pwa-strategy=none` 사용 |

## 9. 완료 산출물 기준

시연 가능한 데모 기준:

- 스테이지 선택부터 전투, 결과, 영구 업그레이드까지 한 흐름이 끊기지 않는다.
- 50라운드 클리어 또는 실패 후 다음 선택지가 명확하다.
- 포탑 5종, 적 4종, 젬 12종이 각자 역할을 갖는다.
- 저장/복구가 진행 중 런을 망가뜨리지 않는다.
- 모바일 세로 화면에서 주요 정보와 버튼이 읽힌다.
- 테스트와 웹 빌드가 통과한다.
