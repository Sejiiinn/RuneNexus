# 업데이트 다운로드 용량 표시·복귀 확인

2026-09-26. [기존 시작 화면 외형](../README.md)을 유지하면서 실제 수신량을 `받은 용량 / 전체 용량 MB`와 로딩바로 표시한다. MB 환산은 기존 버전 용량과 같은 1024×1024 기준이다.

- Android `update_progress`의 실제 쓰기 완료 바이트를 사용한다. 변경분은 변경분 크기, 전체 APK로 재시도하면 전체 APK 크기와 수신량 0으로 전환한다. 파일 확인·변경분 적용은 별도 문구와 불확정 표시를 사용한다.
- 수신량 변경은 진행 표시만 갱신한다. 릴리즈 노트 스크롤·버튼 노드를 재생성하지 않는다.
- 일반 앱 복귀는 다운로드 중 `busy` 가드로 새 확인·다운로드를 시작하지 않는다. Activity/프로세스 재시작이나 설치/재확인 실패 뒤에는 이미 완성된 APK를 목표 버전·크기·해시·패키지·서명으로 재검증해 재사용한다. 검증 실패 파일은 새로 받는다.
- **미완료 전송 중 프로세스가 종료된 경우의 부분 파일 이어받기는 포함하지 않는다.** 사용자 환경에서 발생한 현상의 원인은 직접 기기 기록을 확보하지 못했으므로 일반 앱 전환·재시작·설치 실패를 구분한다.

## Godot 검증

격리 프로젝트 `/tmp/rune-startup-progress-20260926/godot`, Godot 4.7.2, macOS Apple M4 OpenGL Compatibility. 사용자 저장과 분리했다.

- [서비스 검사](service.log): `UPDATE_SERVICE failures=0`. 실제 계약의 진행 이벤트, 잘못된/늦은 이벤트 무시, 변경분 실패→전체 전환, 캐시 검증 실패→0부터 진행, 다운로드 중 재확인 차단.
- [화면·부팅 검사](run.log): `STARTUP_SCREEN failures=0`. 실제 mouse 입력·busy 차단, 진행 갱신 시 스크롤 유지, 앱 복귀 시 추가 확인 없음, MB/비율 연결 및 확인·적용 단계 구분.
- [75% 화면](download-75.png), [320px·글자 2배](download-narrow-large-text.png). 실제 컴포넌트를 테스트 상태로 실행한 캡처이며 운영 업데이트 서버 화면은 아니다.

## Android·독립 검증

- [Kotlin 컴파일](android-kotlin-compile.log), [JVM 10건](android-jvm-tests.log) 통과. 실제 쓰기량·최종 이벤트·100ms 제한·잘못된 길이/HTTP/해시 거부 및 손상 캐시 진행 초기화를 확인했다.
- [Android 수신·복귀](android-device.log): arm64 에뮬레이터에서 실제 singleton과 Godot 서비스를 연결해 512KiB HTTPS 다운로드. 동일 PID에서 HOME 이후 수신을 완료하고 복귀 시 524288바이트를 유지했다. 다운로드 시작 0 이벤트는 한 번이었다. **이 실행에서 복귀 시점은 수신 완료 후**이며, 진행 중 복귀의 중복 요청 차단은 Godot 회귀에서 별도로 확인했다.
- [캐시 검사](android-cache.log): 유효한 서명 APK는 연결 불가능한 URL에서도 재검증만으로 성공했다. 1바이트 손상 후에는 verify 0 → download 0 → 실제 수신을 수행하고 잘못된 해시를 거부했다. 검수용 APK·캐시만 사용했으며 설치기는 호출하지 않았다.
- [검사 APK 점검](android-apk-audit.json): 78,021,093바이트, arm64 단일 ABI, Flutter 없음. 15KiB 테스트 팩을 사용한 분리 검사 APK로 게임 배포 크기를 의미하지 않는다. 검사가 끝난 뒤 네트워크 및 기존 검수 APK를 복원했다. [정식 앱 검사 전](android-production-before.txt)·[검사 후](android-production-after.txt) 버전·업데이트 시각은 동일하다.
- 별도 Astra 검증자가 최종 코드·화면·Godot/Android 검사 원문과 로그를 직접 대조하여 **PASS**. 캐시 후보 검증에서 전체 수신량을 먼저 보고해 재다운로드 진행이 고정되는 결함을 발견했고, verify 0 보고와 관련 회귀로 해결을 확인했다.

물리폰 검증은 수행하지 않았다. 사용자 기기에서 보고한 원인 자체는 미확정이며, OS 프로세스 종료 뒤 미완료 파일 이어받기는 지원하지 않는다.
